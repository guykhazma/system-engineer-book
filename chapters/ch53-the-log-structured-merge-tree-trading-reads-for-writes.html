Chapter 53 — The Log-Structured Merge-Tree: Trading Reads for Writes

Before you start: Chapter 46 (the device measurement that rules everything here: sequential streaming ~916 MB/s versus random 4 KiB access ~19 MB/s, ~49× slower — the gap the LSM-tree exploits), Chapter 41 (durability: an fsync'd append to a log is what makes an in-memory write survive a crash), Chapter 47 (pages and the on-disk file), Chapter 49 (the sequential append a heap file already showed is cheap), Chapter 51 and Chapter 52 (the B-tree — the read-optimized, update-in-place engine this one is the mirror of).  ·  The B-tree finds the page a key belongs on and updates it there, in place, which makes every write a random page update. This chapter builds the engine that refuses to do that: it never updates in place, buffers writes in memory, and flushes them as sorted, immutable files — turning random writes into sequential ones, and paying the bill at read time instead.

The B-tree of the last two chapters is the read-optimized storage engine: it keeps keys sorted in a shallow tree of pages so any key is found in a handful of fetches, and it maintains that order by updating pages in place — finding the leaf a key belongs on and writing it there. That in-place discipline is exactly what makes reads and range scans excellent, and exactly what makes every write a random page update, paying the Chapter 46 random-access cost — ~49× slower than sequential on the very machine we measured. For a write-heavy workload — a metrics firehose, an event log, a high-ingest key-value store — that random-write tax dominates, and no amount of B-tree tuning removes it, because it is inherent in keeping the data sorted on disk as it arrives. The log-structured merge-tree (LSM-tree), introduced by O'Neil, Cheng, Gawlick, and O'Neil in 1996 and made ubiquitous by Google's Bigtable and its descendants (LevelDB, RocksDB, Cassandra, HBase), takes the opposite bet: it never updates in place. Writes go into a sorted in-memory structure and are periodically flushed to disk as whole, immutable, sorted files written sequentially; reads consult memory first and then those files, newest to oldest; and the files are merged in the background to keep their number down. The trade is deliberate and total — the LSM-tree makes writes sequential and cheap and pays for it at read time and in space — and it is the write-optimized counterpart to the read-optimized B-tree. This chapter builds it in five steps: the inversion, and why appending is not enough by itself (§53.1); the write path — the memtable, the write-ahead log that makes it durable, and the flush to an immutable SSTable (§53.2); the read path — check memory, then the sorted files newest to oldest, with a tombstone for deletes, reproduced in a working model (§53.3); the resulting read amplification and space cost that pile up as files accumulate, and its named trap (§53.4); and what all of this hands to the compaction chapter that follows (§53.5).

On the code in this chapter. One Python program (CPython 3.10.12 on this machine's Intel Core i7-12700H) implementing a faithful LSM write and read path: writes land in a sorted in-memory memtable; when it reaches a flush threshold it is written, in sorted order, as an immutable SSTable and a fresh memtable begins; a read checks the memtable and then the SSTables newest to oldest, stopping at the first hit; and a delete writes a tombstone. The program reports two structural quantities — how many SSTables accumulate, and how many of them a point read must scan (its read amplification) — and confirms that the newest write wins and a tombstone shadows older values. These are counts determined by the code's logic and a seeded key stream, not wall-clock timings. Where a sequential-versus-random write cost appears, it is the Chapter 46 device figures (~916 MB/s sequential, ~19 MB/s random) measured earlier in this volume and cited here, not re-measured (a hardware-counter profiler, perf, is not installed on this machine).

53.1 The inversion: make writes sequential, pay at read time

Start from the cost that defines the problem. On the machine of Chapter 46 a large sequential write streams at ~916 MB/s while random 4 KiB access manages ~19 MB/s — a ~49× gap, and it is not an accident of one device: seeks cost on disk, and even flash pays for random writes through its erase-block granularity and garbage collection. A B-tree write is a random write (it updates the leaf a key belongs on), so the B-tree sits on the slow side of that gap for every insert. The obvious escape is to stop seeking: never place a key where it belongs, just append each new key-value to the end of a file in arrival order. Writes are now pure sequential appends at ~916 MB/s — the fast side of the gap. But this naive log has made one thing catastrophic, which is the answer to the opener: a read for a key must now scan the entire log, because the log is in arrival order, not key order, and the key could be anywhere — and if the key was overwritten, the newest value is whichever copy is latest in the log, so you cannot even stop at the first match from the front. An append-only log is the best possible write structure and the worst possible read structure. The LSM-tree is the engineering that keeps the sequential-write win while making reads tractable again, and it does so with one idea: keep the in-memory buffer sorted, and flush it sorted. Then the on-disk files are each internally sorted (so a key is found in one file by binary search, not a scan), and there are few enough of them (because each flush is a whole batch, not one key) that a read consults a manageable handful. The LSM-tree is not “a log” in the naive sense; it is a log of sorted runs, and that word “sorted” is what turns an unreadable append log into a real index. What it cannot escape is that reads now touch several sorted files instead of one tree — the bill the write side deferred — and the rest of the chapter is about paying it.

53.2 The write path: the memtable, the WAL, and the immutable SSTable

A write enters the LSM-tree at the memtable: an in-memory, sorted, mutable structure — typically a balanced tree or a skip list, so inserts stay ordered and cheap — that accumulates recent writes. Because the memtable is in volatile memory, a crash would lose it, so every write is first appended to a write-ahead log (WAL) on disk (Chapter 41) — a sequential, fsync'd append, itself cheap — so that after a crash the memtable can be reconstructed by replaying the log. This is the crucial detail that makes the LSM-tree durable without a random write: the only synchronous disk write on the insert path is a sequential append to the WAL; the sorted placement happens in memory. When the memtable grows past a threshold, it is flushed: its contents, already sorted, are written out in one sequential pass as an immutable on-disk file — historically called an SSTable (Sorted String Table, the name from Bigtable) — and once the SSTable is safely on disk the corresponding WAL segment can be discarded and a fresh empty memtable takes over. Two properties of that flushed file are load-bearing for everything after. It is sorted, so a lookup within one SSTable is a binary search, not a scan, and two SSTables can be merged by a linear merge like the merge step of mergesort. And it is immutable: once written, an SSTable is never modified in place — not to update a key, not to delete one — which is what keeps writes sequential (no random rewrites ever happen) and also makes the files trivially safe to read concurrently and to cache, since nothing mutates underneath a reader. An update to an existing key does not find and change it; it simply writes the new value into the memtable, which will flush to a newer SSTable, and the newer value shadows the old one at read time. The disk fills with a stack of immutable sorted files, newest on top, and no random write was ever issued.

The same idea three ways: buffer in memory and flush sorted, turning random writes into sequential ones

1. In words. Instead of updating the page a key belongs on (a random write), the LSM-tree collects writes in a sorted in-memory memtable and flushes the whole batch as one immutable sorted file in a single sequential pass. Every disk write it issues is sequential; the price is that a key's current value may live in memory or in any of the flushed files.

2. As a picture. Figure 53.1: writes flow into a memtable box; an arrow labeled “flush (sequential)” drops a sorted SSTable onto a growing stack of immutable files below, newest on top; a WAL append sits beside the memtable guarding durability.

3. As numbers. The write the LSM-tree avoids is the ~19 MB/s random 4 KiB update of Chapter 46; the writes it issues — the WAL append and the flush — are the ~916 MB/s sequential stream, the same ~49× faster side of the gap. The cost moves to reads and space, quantified in §53.3–§53.4.

(Answer to the §53.1 quick check: a naive arrival-order append log makes reads catastrophic — a lookup must scan the whole log, since the key could be anywhere and the newest copy is wherever it was last written. The property that makes reads tractable is sortedness: keep the memtable sorted and flush it sorted, so each on-disk file is internally sorted — found by binary search, mergeable linearly — and a read consults a handful of sorted runs instead of scanning an unordered log.)

53.3 The read path: newest wins, tombstones, and read amplification

Because a key's value can live in the memtable or in any flushed SSTable, and because a newer write shadows an older one, a read must consult the sources newest first and stop at the first hit. It checks the memtable; then, if not found, the SSTables from newest to oldest; the first source that contains the key holds its current value, and the search stops — anything older is a superseded version and must not be returned. This ordering is also how deletion works, and the mechanism is worth stating plainly because it surprises people: since SSTables are immutable, a delete cannot go back and erase the key from the older files where it still sits. Instead a delete writes a tombstone — a marker “this key is deleted” — into the memtable, which flushes to a newer SSTable like any other write. A later read finds the tombstone first (it is the newest entry for that key), stops, and reports the key absent, even though older SSTables still physically contain the old value. A delete, in an LSM-tree, is a write. The working model reproduces the whole path — newest-wins reads, tombstone-shadows-value deletes, and the count of files a read must touch:

LSM write path (100000 writes, keys drawn from a 40k-key space so keys are overwritten):
  flush_threshold=1000: 100000 writes -> 99 SSTables on disk
     avg SSTables scanned per point read: hit=35.9   miss=99  (a miss must touch ALL runs)
  flush_threshold=5000: 100000 writes -> 19 SSTables on disk
     avg SSTables scanned per point read: hit= 7.6   miss=19  (a miss must touch ALL runs)

correctness: newest write wins; a tombstone shadows an older value
  put v1, put v2, flush;  put v3, flush   -> get = v3           (newest of two SSTables)
  delete, flush                           -> get = None         (tombstone shadows v2,v3, which still sit on disk)
  SSTables on disk: 3  (the dead values are NOT reclaimed until compaction)

Two facts jump out. First, the model is correct: the newest write wins, and a tombstone hides values that physically still exist in older files — deletion by shadowing, not erasure. Second, and this is the whole cost of the design: a point read may have to scan many SSTables. A lookup for a key that is absent is the worst case — it finds the key in none of them, so it must touch every run before concluding “not here” (99 files at the small flush threshold, 19 at the larger). This is read amplification: the LSM-tree turned one logical read into many physical file probes, the exact mirror of the write amplification a B-tree pays. The flush threshold trades one against the other — a larger memtable means fewer, bigger SSTables (less read amplification) but more memory held and more lost on a crash before the WAL is replayed. And notice the deletion line: after deleting the key, three SSTables still sit on disk, two of them holding now-dead values plus a tombstone. The LSM-tree's write path has quietly created three problems that only grow with time — too many files to read, dead values wasting space, and tombstones that must be carried until every older copy they shadow is gone — and none of them is fixed by anything on the write path. Fixing them is the job of compaction, the next chapter; this chapter's job is to make you feel why compaction is not optional.

Trap: a delete is a write — the tombstone, and the range-scan-over-tombstones cliff

The intuition “deleting frees space and speeds things up” is exactly backwards in an LSM-tree, and it bites hard. A delete does not remove anything: it writes a tombstone, which adds data, consumes a memtable slot and eventually an SSTable entry, and leaves the old value physically on disk in older files until a later compaction finally drops both. So deleting a million keys makes the store temporarily larger, not smaller. Worse is the range scan. A range scan over an LSM-tree must merge the runs across the whole key range and skip past every tombstone in it, because a tombstone might be shadowing a live value in an older run and the scan cannot know without reading it. A key range that has been heavily deleted — say a queue table where rows are inserted and soon deleted, or a time range that was bulk-purged — can therefore hold thousands of tombstones with almost no live rows, and a scan of it reads all of them to return almost nothing: a query that touches “ten live rows” can physically read tens of thousands of tombstones and stall. This is a real and famous operational cliff (Cassandra operators know it as the “tombstone scan” problem, complete with warning thresholds). “It's just a few deleted rows, the query should be fast” and “deletes clean up after themselves” are both false on an LSM-tree: deletes are writes that linger, and reads pay for them until compaction removes them. The honest mental model is that in an LSM-tree every operation, including delete, is an append, and space and read cost are reclaimed only by the background merge — never by the delete itself.

Say it like a systems engineer

Try it first. A teammate says: “We moved our high-ingest service from Postgres to an LSM key-value store and writes got dramatically faster — great. But now point reads are noticeably slower than before, and the data directory is almost twice the size of the actual data. Did we misconfigure something?” Cover the paragraph and answer in four or five sentences, drawing on §53.1–§53.4.

Model answer. “Nothing is misconfigured — you're seeing the LSM-tree's trade working exactly as designed. It made writes fast by never updating in place: writes buffer in memory and flush as immutable sorted files, so every disk write is sequential instead of a random page update. The bill for that lands on reads and space. A point read has to check the memtable and then the sorted files newest-to-oldest, so it probes several files instead of one B-tree — that's read amplification, and it's why reads got slower. And the near-2× size is space amplification: old versions of updated keys and tombstones for deleted keys physically stay in older files until a background compaction merges the files and drops the dead entries. So it's the write-optimized side of a deliberate trade, not a bug. What you tune is compaction — how aggressively the files are merged — which buys back read speed and space at the cost of extra background write work; that's the knob, and it's the subject of the next chapter.” Naming the in-place-vs-append inversion, read amplification, space amplification, and compaction as the knob is the senior register.

53.4 Why the files must be merged: read amplification and space, over time

The write path of §53.2 has one relentless consequence: SSTables only accumulate. Every flush adds a file and none is ever removed by writing, so a long-running LSM-tree drifts toward a large stack of sorted runs, and the read path of §53.3 pays for every one of them. Read amplification grows with the file count — a point miss touches all of them, and even a hit touches every file newer than the one holding the key. Space grows too, and for two distinct reasons the write path guarantees: obsolete versions, because updating a key writes a new copy while the old copy sits in an older file unremoved, so a hot key that is updated a thousand times has a thousand versions on disk with only the newest live; and tombstones, because a delete adds a marker and cannot remove the shadowed value, so deleted data occupies space until every copy it shadows is gone. Left alone, an LSM-tree becomes slower to read and larger on disk without bound, even as its logical contents stay the same size. The structure therefore has a mandatory second half that the write path implies but does not perform: compaction, a background process that reads several SSTables, merges their sorted contents into fewer (or one) new sorted SSTables, and along the way keeps only the newest version of each key and drops tombstones whose shadowed values it has now also seen and discarded. Compaction is what bounds the file count (bounding read amplification), reclaims the space of dead versions and tombstones (bounding space amplification), and it is the reason the “LSM” has “merge” in its name. It is not free — it re-reads and re-writes data that was already written, which is write amplification, the LSM's own version of the B-tree's random-write cost, only deferred and sequential — and how aggressively to run it is the central tuning decision, trading read amplification and space against write amplification. That three-way trade — the amount of extra reading, extra writing, and extra space you accept — is the subject of the next chapter, and it is why there is no single “best” LSM configuration: you choose which of the three to spend.

(Answer to the §53.3 quick check: a read must go newest-first and stop at the first hit because a newer write shadows an older one — the first source containing the key holds its current value, and any older copy is a superseded version that would be wrong to return. A point miss is the worst case because the key is in no source, so the read can never stop early: it must probe the memtable and every SSTable before it can conclude the key is absent — the full read amplification, every time.)

53.5 What to carry forward

The LSM-tree is the write-optimized storage engine, the mirror of the read-optimized B-tree. It exploits the Chapter 46 fact that sequential access is ~49× faster than random by never updating in place: writes go to a sorted in-memory memtable, made durable by a sequential WAL append, and are flushed in one sequential pass as an immutable, sorted SSTable — so every disk write is sequential and no random page update is ever issued (§53.1–§53.2). Reads pay for that: a lookup checks the memtable, then the SSTables newest to oldest, stopping at the first hit; a delete is a write of a tombstone that shadows older values rather than erasing them; and a point miss must touch every file — read amplification, reproduced at 19–99 files scanned in the working model (§53.3). Because files only accumulate and dead versions and tombstones only pile up, the structure requires compaction to merge runs, drop obsolete versions and tombstones, and bound both read amplification and space — at the cost of write amplification (§53.4).

Step back and the two engines of this part are now both on the table, and they are exact opposites built on the same storage manager. The B-tree keeps data sorted on disk and updates it in place: reads and range scans are excellent (one shallow tree, one path), writes are random and expensive, and space is tight (~69% full). The LSM-tree keeps data sorted in memory and appends it to disk in immutable runs: writes are sequential and cheap, reads and range scans pay to merge many runs, and space is loose (dead versions and tombstones linger until compaction). Neither is better; they sit at opposite ends of a trade between the cost of reading, the cost of writing, and the cost of storage — and the next chapter makes that trade precise, showing how compaction strategy lets an LSM-tree slide along it, and why you cannot minimize all three at once. The chapter after builds the read-side rescue the LSM-tree needs — the Bloom filter that lets a point read skip files that cannot contain the key, cutting the read amplification §53.3 measured. And the final chapter of the part puts B-tree and LSM-tree side by side and answers the question the whole part has been building toward: given a workload, which engine, and why. The B-tree gave you fast selective reads; the LSM-tree gives you fast durable writes; the art is knowing which bill you would rather pay.
