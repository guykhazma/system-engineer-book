Chapter 55 — Bloom Filters: Making the LSM Read Path Cheap

Before you start: Chapter 46 (a random device access ~19 MB/s versus sequential ~916 MB/s — the point-read probe a Bloom filter saves is a random access, the expensive kind), Chapter 48 (the buffer pool the filter lives in, and the reads it stops from evicting useful pages), Chapter 53 (the LSM read path — a lookup probes the memtable and every SSTable, the read amplification this chapter attacks), Chapter 54 (compaction bounds the run count but does not eliminate it; a point read still touches several runs, and the RUM read cost this chapter buys down).  ·  Chapter 54 bounded the LSM-tree's read amplification but left it above one: a point read — above all a point miss — still probes several sorted runs, each a random device access. This chapter is the read-side companion to compaction: the Bloom filter, a tiny in-memory structure that lets a read skip runs that provably cannot hold the key, driving the probes per lookup back toward one.

Compaction (Chapter 54) bounded how many sorted runs an LSM-tree accumulates, but a point lookup still has to consult them: it checks the memtable, then each run from newest to oldest, and only a run whose key range and index say the key could be present is worth a device access. For a key that is present this usually resolves in the first run or two. For a key that is absent — a miss, which in real workloads is common (an existence check, an insert-if-not-present, a lookup for a deleted or never-written key) — there is nothing to short-circuit the search, and the read pays a random device access at run after run only to find the key in none of them. That is read amplification at its worst, and it is exactly the cost the Bloom filter was built to cut. A Bloom filter is a small bit array plus a handful of hash functions that answers one question about a set — is x a member? — with a deliberate asymmetry: it can say “definitely not” with certainty, or “possibly yes” with a small, tunable error. Put one in front of each SSTable and a point read consults the filters first, skipping every run whose filter says “definitely not” without touching the disk at all. This chapter builds it from the bits up: why an LSM point miss is the costly case (§55.1); the structure and its one-sided error, invented by Bloom in 1970 (§55.2); the false-positive-rate arithmetic — the closed-form formula, the optimal number of hashes, the bits-per-element for a target error — reproduced against a working filter on real runs (§55.3); how filters slot into the LSM read path, what they cost, and the one thing they cannot help — the range scan (§55.4); and what this completes about the LSM read path (§55.5).

On the code in this chapter. One Python program (CPython 3.10.12 on this machine's 12th Gen Intel Core i7-12700H) in three parts. First a working Bloom filter — a bit array with double hashing — into which 100,000 keys are inserted; it is then probed with 100,000 absent keys and the measured false-positive rate is compared, at several memory budgets, against the closed-form prediction (1 − e^(−kn/m))^k. Second a design table: the bits-per-element and optimal hash count for a range of target false-positive rates, from the same closed-form arithmetic. Third an LSM read-amplification model: how many runs a point miss actually probes with filters at a given error rate versus without. The empirical false-positive numbers are measured on this machine and labeled empirical; the formula, the bits-per-element, and the run-probe figures are exact arithmetic of the model, labeled analytical. No wall-clock timings appear (a hardware-counter profiler, perf, is not installed on this machine); the point of the chapter is the error rate and the memory, both of which are hardware-independent.

55.1 The read the LSM still pays: the point miss

Recall the LSM read path from Chapter 53. To look up a key, the engine checks the in-memory memtable, then walks the on-disk sorted runs from newest to oldest; within a run, a sparse index and the run's key range tell it whether the key could be inside and, if so, which block to fetch. For a key that is present, the search usually stops early — the value is likely in the memtable or a recent run — so a hit is cheap. The punishing case is the point miss: a lookup for a key that is in none of the runs. Nothing stops the search early, because no run can prove the key's absence from its key range alone (the missing key may fall squarely inside a run's minimum-to-maximum span), so the read fetches a block from run after run, each a random device access at Chapter 46's slow ~19 MB/s, and finds nothing every time. With compaction holding the tree at, say, ten runs, a single miss can cost ten random reads to answer “no.” And misses are not rare: existence checks, insert-if-absent, lookups of keys that were deleted or never written — all are misses, and all pay full read amplification. Compaction (Chapter 54) bounded the number of runs but could not drive it to one without paying ruinous write amplification, so the read cost of the miss is real and structural. What is needed is a way to answer “this key is definitely not in this run” without touching the run — a per-run membership summary small enough to keep in memory for every run at once. That is the Bloom filter.

55.2 The Bloom filter: k hashes, m bits, one-sided error

A Bloom filter for a set of n keys is an array of m bits, all initially zero, together with k independent hash functions, each mapping a key to one of the m bit positions. To insert a key, hash it with all k functions and set the k bits they name to one. To test a key, hash it the same way and look at those k bits: if any one of them is zero, the key was certainly never inserted — setting bits is the only thing insertion does, so a present key would have set all k — and the filter answers “definitely not a member.” If all k bits are one, the filter answers “possibly a member,” because those bits might all have been set by other keys whose hashes happened to overlap this one's. That is the filter's defining one-sided error: it never produces a false negative (it never says “not present” about a key that is present), but it may produce a false positive (say “possibly present” about a key that is absent). The asymmetry is exactly what an LSM read needs — a “definitely not” lets the read skip the run with certainty, and a false “possibly” costs only a wasted device access that finds nothing, degrading gracefully to the no-filter behavior rather than returning a wrong answer. This is the structure Burton Bloom introduced in 1970, in a paper whose title names the bargain precisely: a space/time trade-off in hash coding with allowable errors — accept a small, controlled error rate and buy a large reduction in space and probes.

Answering the opener's second question directly: no, such a summary can never say “not here” about a key that is present. The whole point of the one-sided error is that “definitely not” is always trustworthy; only “possibly” can be wrong. That is what makes it safe to put in front of an authoritative store — a “definitely not” skips the run correctly every time, and a false “possibly” merely wastes one probe that the store then resolves. (Answer to the §55.1 quick check: a point miss is worst because nothing short-circuits the search — no run can rule the key out from its key range, so the read fetches a block from every run, ~ten random accesses in a ten-run tree, to answer “no.” The summary that cuts that toward one is a per-run membership filter that can cheaply answer “definitely not in this run.”)

The same idea three ways: a Bloom filter is one-sided membership in a shared bit array

1. In words. Insertion sets k hashed bits; a test that finds any of a key's k bits still zero proves the key was never inserted (“definitely not”), while all-ones means “possibly” — the bits may be borrowed from other keys. Absence is certain; presence is a guess. So the filter never has a false negative, only a false positive.

2. As a picture. Figure 55.1: one bit array; key A's three arrows land on three positions and set them; a query for absent key Z whose three arrows include a still-zero cell is rejected outright, while a query for absent key Y whose three cells all happen to be one is a false positive — a “maybe” the store will disprove.

3. As numbers. At 10 bits per key with the optimal k=7 hashes, the measured false-positive rate on 100,000 inserted and 100,000 absent keys is about 0.9% (§55.3) — under one wasted probe in a hundred misses, for ten bits of memory per key and zero risk of a wrong “no.”

55.3 The false-positive rate: formula, optimal k, and bits per element

How often does the filter say “possibly” about an absent key? After inserting n keys into m bits with k hashes, the probability that any one bit is still zero is (1 − 1/m) raised to the kn power, which for the sizes that matter is very close to e^(−kn/m). A false positive requires all k of a query's bits to be one, so the false-positive rate is approximately p ≈ (1 − e^(−kn/m)) raised to the k power. Two design facts fall out of that formula. First, for a fixed memory ratio m/n there is an optimal number of hashes that minimizes p: k* = (m/n) ln 2 — too few hashes and each test checks too little; too many and the bits fill up too fast. Second, at that optimum the error falls exponentially in the bits per element: to hit a target rate p you need m/n = −ln p / (ln 2) squared bits per key — a fixed budget per key, independent of how many keys there are. The first part of the program builds a real filter (double hashing to synthesize k indices from one hash), inserts 100,000 keys, probes 100,000 absent keys, and lays the measured rate beside the formula:

empirical FPR vs formula  (n=100000 inserted, 100000 absent probes)
  bits/elem   k    formula FPR    empirical FPR
     4      3       0.14689       0.14654
     8      6       0.02158       0.02103
    10      7       0.00819       0.00875
    12      8       0.00314       0.00320
    16     11       0.00046       0.00055

The measured false-positive rate tracks the closed-form (1 − e^(−kn/m))^k across two orders of magnitude — at 10 bits per key the formula predicts 0.82% and the filter delivers 0.88%; the small gaps are ordinary sampling noise over 100,000 probes, not a modelling error. The shape is the whole story: each additional handful of bits per key cuts the error by roughly a constant factor, because the error decays exponentially in m/n. That is why a filter can be so cheap — you do not pay per stored value, only a fixed few bits per key, and a little memory buys a lot of certainty. The design table makes the budget explicit, computed from the two closed forms above:

design table: bits/element and optimal k for a target FPR
  target FPR   bits/elem (m/n)   optimal k
    0.1000          4.79           3.32
    0.0500          6.24           4.32
    0.0100          9.59           6.64
    0.0010         14.38           9.97
    0.0001         19.17          13.29

Read the table as a price list. A 1% false-positive rate — one wasted probe per hundred misses — costs about 9.6 bits per key, call it a byte and change; a ten-times-stricter 0.1% costs about 14.4 bits, and each further factor of ten adds a near-constant ~4.8 bits (that is 1/(ln 2) squared bits per decade). For an LSM-tree holding a billion keys, a 1% filter is roughly 1.2 GB of memory spread across the runs — small enough to keep resident, and the reason production engines attach a Bloom filter to every SSTable by default. The optimal k is not a free parameter to guess: it is fixed by the memory you spend, and the table's values (7 hashes at 10 bits, matching the empirical run above) are where the error is least for that budget.

Trap: a Bloom filter never lies about absence — but that is the only promise it makes

The one-sided error is so clean that it invites three overreaches, each a real production bug. First, “false positives don't matter, they just cost one probe.” They cost one probe each, and at the wrong error rate that adds up: a filter sized for 10% false positives in front of a ten-run tree still lets roughly one miss in ten fall through to a wasted run probe, and across a firehose of existence checks that is a large fraction of the read work the filter was supposed to remove — the error rate is a capacity decision, not a detail. Second, “a Bloom filter can tell me the key is present.” It cannot: “possibly” is never a yes. Any read that treats a filter hit as a confirmed membership — skipping the authoritative lookup — will occasionally return a value for a key that was never stored, which is data corruption, not a performance bug. The filter guards the store; it never replaces it. Third, “I'll just delete keys from the filter by clearing their bits.” A standard Bloom filter cannot support deletion — clearing a key's k bits may clear bits another key relies on, which would create a false negative and break the one promise the structure makes; deletion needs a counting Bloom filter or a different structure such as the cuckoo filter (Fan et al. 2014), which supports deletes at comparable space. The honest posture: a Bloom filter proves absence and only suggests presence, its error rate is a memory-budget decision you make deliberately, and you never mutate it in ways that could manufacture a false negative — because the instant it can say “not present” about a present key, it is worse than useless in front of a store that must be correct.

Say it like a systems engineer

Try it first. A teammate proposes: “Our LSM point lookups are slow on misses. Let's add a Bloom filter with, say, 4 bits per key to keep the memory tiny — and while we're at it, we can skip the SSTable read entirely when the filter says the key is present, since the filter already told us it's there.” Cover the paragraph and answer in four or five sentences, drawing on §55.2–§55.3.

Model answer. “A Bloom filter is exactly the right fix for slow misses — it turns most miss probes into an in-memory ‘definitely not’ and never risks a wrong answer, because it has no false negatives. But two of the specifics are off. Four bits per key gives about a 14% false-positive rate, so roughly one miss in seven still pays a wasted run probe; if misses are our pain, we want ~10 bits per key for about 1%, which is still only a bit over a gigabyte for a billion keys. And we can't skip the SSTable read on a filter hit: ‘possibly present’ is never a confirmed yes, so trusting it would let us return values for keys that were never stored — a correctness bug, not a speed-up. The filter's job is to skip runs that are definitely absent; every ‘maybe’ still goes to the store. So: yes to the filter, size it for ~1% not tiny, and keep the authoritative read on every hit.” Naming the false-negative-free asymmetry, the bits-per-element cost of the target rate, and the “guard not replace” rule is the senior register.

55.4 Filters in the LSM: skipping runs, and the range-scan gap

Now put a filter in front of each SSTable and rerun the point-miss path of §55.1. The read consults each run's Bloom filter first; a “definitely not” skips that run with no device access, and only a “possibly” — a genuine hit or a false positive — triggers the block fetch. For a true miss, every run's filter should say “definitely not,” and does except for the false-positive fraction p, so the expected number of runs actually probed collapses from L to about L×p. The third part of the model tabulates it:

LSM point-read miss: runs actually probed (L levels), Bloom at FPR p
  levels L   no filter   with Bloom p=0.01   with Bloom p=0.001
     4          4               0.040               0.004
     7          7               0.070               0.007
    10         10               0.100               0.010
  (expected wasted probes = L*p; a true miss with p=0.01, L=10 => ~0.1 disk probes vs 10)

The point miss that cost ten random device accesses now costs, in expectation, about one tenth of one access at a 1% filter — read amplification for the miss falls by two orders of magnitude, and with it the read half of the RUM trade the LSM-tree pays. This is why the Bloom filter is the standard companion to compaction: compaction bounds how many runs exist, and the filter makes the point read pay for only the runs that might actually contain the key. It also sharpens Chapter 54's whole picture — with filters, an LSM-tree's point-read amplification is near the B-tree's, so the remaining gap between the families narrows to range scans and the write/space trade. One subtlety is worth the senior engineer's attention, and it is the insight behind the Monkey design of Dayan and colleagues (2017): the total false-positive cost of a lookup is the sum of the per-run false-positive rates, so spending the same memory unevenly — more bits per key on the larger, more numerous lower levels and fewer on the small upper ones — minimizes the expected wasted probes for a fixed memory budget, rather than giving every run the same bits per key. The tuning of the filter is itself part of the LSM's read/memory trade.

There is one read the filter cannot help at all, and naming it is half of understanding filters: the range scan. A Bloom filter answers only point membership — “is this exact key present?” — and says nothing about which keys fall in an interval, because hashing destroys order. A query for all keys between a and b must still open every run whose key range overlaps [a, b] and merge their contents; the filter offers no skip, because a run may hold some key in the range even when it holds none of the specific keys you might name. This is the structural reason the B-tree keeps its edge on range-heavy workloads even after the LSM-tree gets Bloom filters: the filter buys back point-read amplification but not scan amplification, and the range scan is where sorted, clustered, in-place storage still wins. (Structures that do summarize ranges, such as the prefix or succinct range filters that extend this idea, exist, but the plain Bloom filter is a point-membership structure, full stop.)

55.5 What to carry forward

The Bloom filter is a small in-memory bit array with k hash functions that answers set membership with a deliberate one-sided error: definitely not a member is always correct, possibly a member may be a false positive, and a false negative never occurs (§55.2). Its false-positive rate is p ≈ (1 − e^(−kn/m))^k, minimized at k* = (m/n) ln 2, and reaching a target p costs a fixed m/n = −ln p/(ln 2) squared bits per key — about 10 bits for 1%, verified against a working filter whose measured rate matched the formula across two orders of magnitude (§55.3). Placed in front of every SSTable, a filter lets a point read skip runs that are definitely absent, cutting a point miss from L probes to about L×p — ten random accesses down to ~0.1 at 1% (§55.4). The named trap: a Bloom filter proves absence but only suggests presence, so it guards the store and never replaces it, its error rate is a memory-budget decision, and it cannot be safely deleted from — nor can it help a range scan, which needs order the hash destroys (§55.3–§55.4).

With the Bloom filter the LSM read path is complete. Chapter 53 built it, Chapter 54 bounded its amplification with compaction, and this chapter drove the point-miss cost back toward one — so the LSM-tree now offers cheap sequential writes, tunable write/space amplification, and point reads competitive with a B-tree, with only the range scan and the write/space cost left as genuine differences between the families. That is exactly the comparison the part has been building toward, and it is now fully in hand: two storage engines, each measured on read, write, and space; a shared amplification vocabulary; the compaction dial; and the Bloom filter that closes the read gap. The part's final chapter spends this vocabulary on the question every database designer eventually faces — given a concrete workload, B-tree or LSM-tree, and at what settings? — turning the whole part into a decision procedure. Everything since Chapter 46 has been assembling the terms of that decision; next we make it.
