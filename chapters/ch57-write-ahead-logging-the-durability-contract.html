Chapter 57 — Write-Ahead Logging: The Durability Contract

Before you start: Chapter 41 (fsync, the page cache, and what it actually takes to force bytes to the device — the primitive the log's durability rests on), Chapter 46 (sequential ~916 MB/s versus random ~19 MB/s — why appending to a log is cheap and flushing scattered data pages is not), Chapter 48 (the buffer pool: dirty pages that live in volatile memory until written back — the state a crash erases), Chapter 53 (the LSM memtable: acknowledged writes held in memory before the flush — the same exposure).  ·  The storage engines of the last part all keep freshly written data in volatile memory — the buffer pool's dirty pages, the LSM's memtable — until it reaches disk. This part confronts the failure they all assumed away: the machine loses power mid-write. The write-ahead log is the first and deepest answer — the mechanism by which a database can promise a committed write survives a crash, and prove it.

Every storage engine in the last part shares a quiet assumption: that the machine keeps running. A B-tree update lands first in a buffer-pool page that is dirty — modified in memory, not yet written back (Chapter 48) — and an LSM write lands in the in-memory memtable, acknowledged to the client but not yet flushed to an SSTable (Chapter 53). In both, there is a window — often a long one, because writing back is deferred precisely to batch it — in which the database has told the client the write succeeded while the only copy lives in volatile memory. Pull the power in that window and the write is simply gone: the buffer page never reached disk, the memtable evaporated, a half-finished compaction left the files inconsistent. This is the durability problem, the D of ACID, and it is not a rare edge case — power fails, kernels panic, processes are killed — so a database that means its acknowledgments must have an answer. The naive answer, flush everything to disk before acknowledging, is correct but ruinous: it turns every commit into scattered random writes of large data structures at Chapter 46's slow ~19 MB/s, destroying the very write performance the engines were built for. The write-ahead log is the answer that keeps both durability and speed. Before applying a change to the volatile data structure, the database first appends a small record describing the change to a log — a single sequential file — and forces that to disk; the large data structure is written back lazily, whenever convenient. If a crash intervenes, recovery replays the log to reconstruct exactly the state that was lost. This chapter builds the idea from the failure up: what a crash actually destroys and why every engine is exposed (§57.1); the durability contract and the force-versus-log dilemma it creates (§57.2); write-ahead logging itself — log the intent, apply lazily, replay to recover — reproduced on a working store that survives a simulated crash (§57.3); the write-ahead rule that makes it correct and the sequential append that makes it cheap (§57.4); and what this opens for the rest of the part (§57.5).

On the code in this chapter. One Python program (CPython 3.10.12 on this machine's 12th Gen Intel Core i7-12700H) that builds a tiny key-value store whose only durable artifact is an append-only redo log. It applies a deterministic workload of 1,000 operations (puts, overwrites, deletes) — appending and fsync-ing a log record before mutating the in-memory map each time — then simulates a crash by discarding the in-memory state entirely, and finally recovers by replaying the log from the start. It reports the live key count before the crash, after the crash, and after recovery, and checks that the recovered state exactly equals the pre-crash state. This is a deterministic, structural demonstration — the recovered state either matches or it does not, and it does — not a wall-clock timing (perf is not installed on this machine, and the point is correctness of recovery, not its speed). The one performance fact used, that a sequential append is far cheaper than flushing scattered data pages, is Chapter 46's measured figure, cited, not re-measured.

57.1 The crash: what volatile state a failure destroys

Start with what is actually lost when the power fails. A running database holds most of its recent work in volatile memory — memory whose contents vanish when power does. The buffer pool (Chapter 48) caches data pages, and a page that has been modified but not yet written back is dirty: its new contents exist only in RAM. The LSM memtable (Chapter 53) holds writes that were acknowledged to the client but not yet flushed to an immutable SSTable: again, only in RAM. Both designs defer the write to disk on purpose — to batch many changes into few large sequential writes rather than many small random ones — which means the volatile window is not an accident but a deliberate, and often lengthy, part of how the engine earns its performance. The consequence is stark: at any instant, some set of acknowledged writes exists nowhere but in memory. A crash in that window destroys them with no trace — the client was told “committed,” but after reboot the data is gone, a broken promise. Worse than lost writes is inconsistency: a crash can strike halfway through a multi-page update (a B-tree node split that wrote one page but not its sibling) or a compaction (Chapter 54) that wrote some output but not all, leaving the on-disk structure not merely stale but corrupt — a tree with a dangling pointer, an index that disagrees with its table. So a crash threatens two distinct things: durability (acknowledged writes must survive) and consistency (the on-disk structure must never be left in a state no valid sequence of operations could produce). Any recovery mechanism must deliver both, and it must do so knowing it can be interrupted again at any point, including during recovery itself.

57.2 The durability contract, and the force-versus-log dilemma

Durability is a contract: once the database acknowledges a write as committed, that write must survive any subsequent crash. Stated so plainly it seems to force an obvious implementation — before acknowledging, write the new data all the way to disk with fsync (Chapter 41) so it is truly durable, then reply. This is the force policy, and it is correct but catastrophic for performance, for exactly the reason the storage engines deferred writes in the first place: the data structure is large and its changed pages are scattered, so forcing them on every commit means many small random writes at Chapter 46's slow ~19 MB/s, plus an expensive fsync each time — it throws away the batching that made the engine fast and caps commit throughput at the device's random-write rate. The way out is to separate the two things the force policy conflated: durability of the change and placement of the data in its final structure. You do not need the data in its final scattered home to make it durable; you only need enough information to reconstruct it saved somewhere cheap. That somewhere is the log: a single, append-only file to which you write a small record describing each change — “key k was set to v” — and force that to disk before acknowledging. Because the log is append-only, every write to it is sequential, at Chapter 46's fast ~916 MB/s, and each commit forces one small record at the end of one file instead of scattering writes across a large structure. The large data structure itself is written back lazily, whenever convenient, because its durability is already guaranteed by the log. This is the answer to the opener: the small cheap record is a log record, forced to disk in place of the whole structure, and after a crash you replay those records to rebuild the lost state. The policy has a name — no-force (do not force the data pages on commit) with logging — and it is the foundation of every durable database.

(Answer to the §57.1 quick check: acknowledged-but-unpersisted writes live in the buffer pool's dirty pages and the LSM's memtable; the engines keep data there on purpose to batch many small changes into few large sequential writes rather than paying a random write per change. Beyond losing writes, a mid-update crash can leave the on-disk structure inconsistent — corrupt, like a tree with a half-written node split — a state no valid operation sequence could produce.)

The same idea three ways: log the intent before you apply it, replay to recover

1. In words. Before changing the volatile data structure, append a small record of the change to a sequential log and force it to disk; acknowledge only after the log record is durable, and write the data structure back lazily. After a crash, replay the log from the start to reconstruct every acknowledged change — the durable log is the source of truth.

2. As a picture. Figure 57.1: two lanes. The top lane is the append-only log growing rightward, each commit forcing one record to disk; the bottom lane is the large data structure, written back occasionally and lazily. A lightning bolt (crash) erases the bottom lane's in-memory part; a replay arrow reads the top lane back into the bottom to restore it.

3. As numbers. The working store applies 1,000 operations, forcing 1,000 log records; a crash drops all in-memory state (163 live keys → 0); replaying the 1,000 records restores exactly 163 keys, and the recovered map equals the pre-crash map — True (§57.3).

57.3 Write-ahead logging: log the intent, apply lazily, replay to recover

The working store makes the mechanism concrete. Its only durable artifact is an append-only redo log of records like PUT k v and DEL k. Every operation does two things in a fixed order: first it appends and forces the log record (write then fsync, Chapter 41), then it applies the change to an in-memory dictionary — the volatile “data structure” standing in for a buffer pool or memtable. After 1,000 operations we simulate a crash by throwing the dictionary away — modelling the power loss that erases all volatile state — and then recover by replaying the log from the beginning, re-applying each record to a fresh dictionary:

write-ahead logging: crash + redo recovery
  operations applied: 1000   live keys before crash: 163
  log records on disk: 1000
  after crash, in-memory keys: 0   (volatile state gone)
  no-log store would recover: 0 keys (state was only in memory)
  replayed 1000 log records
  live keys after recovery: 163
  recovered state EXACTLY matches pre-crash state: True

The three-line arc is the whole idea. Before the crash, 1,000 operations left 163 live keys in memory and, crucially, 1,000 records on disk — the log holds the complete history of acknowledged changes, durably, even though the data structure itself was never written back. The crash takes the in-memory dictionary to zero keys; a store with no log would recover nothing, because its only copy was the volatile one — exactly the exposure of §57.1. Recovery replays all 1,000 records into a fresh dictionary and reconstructs precisely 163 live keys, and the recovered map equals the pre-crash map exactly — True. That equality is the durability contract kept: every acknowledged write survived, because every acknowledged write was preceded by a forced log record, and the log outlived the crash. Notice what recovery is: a deterministic redo, re-applying the logged changes in order to a clean slate — overwrites and deletes replay to the same final state because the log preserved their order. Notice too what the store never did: it never wrote the dictionary to disk at all. All its durability came from the small sequential log, not from persisting the large structure — which is the no-force payoff of §57.2 in action, and why real engines can acknowledge a commit at the speed of one sequential append rather than one scattered flush.

Trap: the log you wrote but never forced — buffered “durability” that a crash erases

The write-ahead log is only as durable as the fsync behind it, and the most common recovery bug is a log that was written but never truly forced — durability theater that works in every test except a real power loss. It has three faces. First, the missing fsync: calling write() on the log copies bytes into the OS page cache and returns, but the bytes may sit in RAM for seconds before the kernel flushes them (Chapter 41); crash in that window and the “durable” log record is as gone as the data it was meant to protect. A log write must be followed by fsync (or opened with the right synchronous flags) before the commit is acknowledged, or the contract is a lie. Second, ordering — the write-ahead rule itself: if the data page reaches disk before its log record (say the OS flushes the big structure while the small log record still sits buffered), a crash can leave a change in the data with no log entry to explain or undo it — the log must be forced ahead of the data it describes, which is the rule the whole scheme is named for (§57.4). Third, “the disk said it's written”: some devices and volatile write caches acknowledge an fsync before the bytes hit stable media, so a crash loses supposedly-forced records; a database that means its durability must ensure the flush reaches truly stable storage (barriers, disabled volatile caches, or battery-backed ones). The counter-trap is over-forcing — fsync-ing on every tiny operation when a group commit could force one batch of records for many concurrent transactions at once, recovering throughput without weakening the contract. The honest posture: durability equals a forced log record ahead of the data change and ahead of the acknowledgment, all the way to stable media — anything short of that is a log that looks durable until the one crash that matters.

Say it like a systems engineer

Try it first. A teammate proposes: “Our commits are slow because we fsync the whole data file on every write. Let's stop doing that and just keep the data in memory, writing it to disk once a minute — the OS buffers our log writes anyway, so we won't lose anything.” Cover the paragraph and answer in four or five sentences, drawing on §57.2–§57.4.

Model answer. “You're right that forcing the whole data file per commit is the wrong cost — that's the force policy, and it's exactly what write-ahead logging avoids. The fix is to stop forcing the data and instead force a small, sequential log record per commit, then write the data structure back lazily; that keeps durability at the price of one append, not one scattered flush. But two parts of the plan break the contract. Keeping data in memory and flushing once a minute with no forced log means a crash loses up to a minute of acknowledged writes — the durability we're promising clients. And ‘the OS buffers our log writes anyway’ is the trap: a buffered write() isn't durable until fsync reaches stable media, so we must force the log record — ahead of the data and ahead of the ack — every commit, or batch them with group commit. So: yes to no-force on the data, but only with a forced write-ahead log; the log is what lets us defer the data safely.” Naming no-force, the write-ahead rule, and the fsync/group-commit reality is the senior register.

57.4 The write-ahead rule, and why the log is cheap and correct

The scheme has one inviolable ordering constraint, and it is the rule the technique is named for. The write-ahead rule: the log record describing a change must reach stable storage before the change itself is allowed to reach the data on disk, and before the commit is acknowledged to the client. The reason is symmetric to the two failures of §57.1. If a data page were allowed to hit disk before its log record, a crash in between would leave a change in the durable data with no log entry to record it — recovery could neither redo it consistently nor undo it, and the on-disk structure could be left inconsistent with no way to repair it. Forcing the log first guarantees that the durable log is always at least as new as the durable data: anything that made it into the data is described in the log, so recovery can always reconstruct or roll back to a consistent state by reading the log alone. This is why the log is the single source of truth and why its ordering, not merely its existence, is what makes recovery correct. And the reason the whole scheme is affordable is Chapter 46: the log is one append-only file, so forcing it is a sequential write at ~916 MB/s, whereas forcing the scattered data structure would be random writes at ~19 MB/s — roughly a 48× difference. Write-ahead logging converts the durability cost from many random writes of a large structure into one sequential append of a small record, which is the same sequential-beats-random insight that powered the LSM-tree, now applied to durability. Correct because the log leads the data; cheap because the log is sequential — those two properties, ordering and sequentiality, are the whole of why write-ahead logging works.

57.5 What to carry forward

A crash destroys volatile state — the buffer pool's dirty pages and the LSM's memtable — so at any instant some acknowledged writes exist only in memory, and a mid-update crash can also leave the on-disk structure inconsistent (§57.1). Durability requires that acknowledged writes survive, but the naive force policy — flush the scattered data structure on every commit — caps throughput at the device's random-write rate; the way out is no-force with logging: force a small, sequential log record per commit and write the data back lazily (§57.2). A write-ahead log appends a redo record before applying each change and replays the log after a crash to reconstruct the lost state — demonstrated on a store that lost all 163 in-memory keys to a crash and recovered them exactly by replaying 1,000 forced records (§57.3). Correctness rests on the write-ahead rule — the log record must reach stable storage before the data it describes and before the acknowledgment — which keeps the durable log at least as new as the durable data; affordability rests on the log being sequential (~916 vs ~19 MB/s, Chapter 46). The named trap: a log write()-n but not fsync-ed, or forced after the data, is durability theater a real crash erases (§57.3–§57.4).

This chapter established the contract and the mechanism, but it left the recovery deliberately simple — replay the entire log from the beginning into an empty store — and that simplicity hides the questions the rest of the part must answer. Replaying all history is fine for a thousand records and impossible for a log that has grown for months; the fix is the checkpoint, a periodic marker that lets recovery start near the end of the log instead of the beginning. Our store logged only redo records and every logged change had been acknowledged; a real database must also handle uncommitted changes that reached the log or the data before a transaction aborted or a crash struck mid-transaction, which requires undo as well as redo, and a disciplined story about what state the data pages can be in at crash time. And the whole apparatus — redo, undo, checkpoints, and the exact protocol that makes recovery correct even when the crash lands during recovery — was worked out in one landmark algorithm, ARIES (Mohan et al. 1992), which the next chapters build up to. Write-ahead logging is the load-bearing idea beneath all of it: log the intent before the act, force the log ahead of the data, and a database can promise durability across a crash and prove it. The engines of the last part store the data; the log is how they keep their word.
