Chapter 58 — Redo, Undo, and the Log Sequence Number

Before you start: Chapter 57 (write-ahead logging, redo recovery, and the write-ahead rule — the mechanism this chapter completes), Chapter 48 (the buffer pool and page eviction — the moment an uncommitted change can be stolen to disk), Chapter 41 (fsync and stable storage — what “durable” actually requires), Chapter 46 (sequential ~916 MB/s versus random ~19 MB/s — why the log is one file).  ·  Chapter 57's store logged only redo and every logged change had already been acknowledged, so recovery was a clean replay. A real database is messier: transactions abort, and a page holding an uncommitted change can reach disk before the transaction that made it commits. This chapter adds the missing half — undo — and the numbering, the log sequence number, that makes both halves correct and idempotent.

Before you read on

From memory: (1) Chapter 57 — what is the write-ahead rule, and what did the redo log let recovery reconstruct? (2) Chapter 48 — when the buffer pool needs a free frame and evicts a dirty page, what happens to that page's contents, even if the transaction that dirtied it has not committed? (3) Predict: a transaction updates a row, its dirty page is evicted to disk, and then the transaction aborts (or the machine crashes) before it commits. The redo log can re-apply committed changes, but this change was never committed and it is already on disk. What extra information would recovery need to remove it, and where would that information have to live? Write your guess; §58.2–§58.3 answer it.

Chapter 57 proved that a forced redo log makes acknowledged writes survive a crash. It did so by assuming two things that a real engine cannot: that every logged change belonged to a transaction that committed, and that recovery could safely replay from the very beginning into an empty store. Drop the first assumption and a new failure appears. Transactions are not single writes; a transaction is a group of changes that must take effect all-or-nothing (the A of ACID, atomicity), bracketed by a begin and either a commit or an abort. Between those brackets its changes are provisional — and yet the buffer pool, which knows nothing of transactions, may evict a dirty page holding one of them to make room, writing a provisional change to disk (Chapter 48). If that transaction then aborts, or the machine crashes before it commits, the change is durable but wrong: it belongs to a transaction whose effects must vanish entirely. Redo cannot fix this — redo re-applies changes, it does not remove them. The database needs the opposite operation, undo: the ability to roll a change back, which means the log must record not only the new value (redo information) but also the old value it replaced (undo information). This chapter builds that: the transaction and why undo is unavoidable (§58.1); the buffer-policy space — steal and no-force — that decides exactly when redo and undo are each required (§58.2); a working store that logs both and rolls back an uncommitted transaction after a crash (§58.3); and the log sequence number and its on-page twin, the page LSN, that make redo idempotent and recovery safe to restart (§58.4). By the end, recovery is correct under the messy reality that Chapter 57 assumed away, and the stage is set for ARIES.

On the code in this chapter. One Python program (CPython 3.10.12 on this machine's 12th Gen Intel Core i7-12700H) that builds a tiny page store whose write-ahead log carries both redo (the after-image) and undo (the before-image) for each change, every record stamped with a monotonic LSN; each data page carries a page LSN, the LSN of the last change applied to it. It runs a workload of two transactions — one that commits, one that does not — arranges for one page to be stolen to disk carrying the uncommitted change while another committed change is lost from memory, then recovers: a redo pass that repeats history (skipping changes already on their page, by comparing LSNs) and an undo pass that rolls back the uncommitted transaction. It prints how many records redo applied versus skipped, how many updates undo reversed, and checks that the recovered state exactly equals the committed-only state. This is a deterministic, structural demonstration — the recovered state either matches the committed-only expectation or it does not, and it does — not a wall-clock timing (perf is not installed on this machine, and the point is correctness). Performance facts (sequential versus random) are Chapter 46's measured figures, cited, not re-measured.

58.1 The transaction, and why redo alone is not enough

Chapter 57's log recorded independent, already-committed operations. Real work comes in transactions: a bracketed group of changes — begin, some updates, then commit or abort — that the database must make atomic, so that either all of the group's changes take effect or none do. Commit is the promise-keeping point of Chapter 57: once a transaction commits, its changes must survive (durability), which is why the commit forces the log. But atomicity introduces a symmetric obligation on the other side. A transaction that aborts — because the application asked to roll back, or a constraint failed, or the transaction was chosen to break a deadlock (a hazard we meet in the next part) — must leave no trace: every change it made must be reversed as if it never happened. And a transaction that is simply in flight when the machine crashes is, for recovery's purposes, an abort it never got to request: it never reached commit, so by atomicity its changes must not survive. Call such a transaction a loser — active at the crash, never committed — and its opposite, a committed transaction, a winner.

Now the problem. Redo, from Chapter 57, re-applies logged changes to reconstruct state that was lost from memory — it is exactly what a winner needs, so its committed changes survive even if their pages never reached disk. But a loser needs the reverse. Suppose a loser updated a row, its dirty page was evicted to disk by the buffer pool (Chapter 48 — the pool has no idea the transaction is uncommitted; it just needs a free frame), and then the machine crashed. The change is now durably on disk, attached to a transaction that must have no effect. Redo cannot help: replaying the log re-applies the change, and doing nothing leaves it in place — either way the loser's write persists, violating atomicity. The only fix is to remove it, to restore the value the page held before the loser touched it. That is undo, and it needs information redo never had: the before-image, the old value. So a real log records two things per change — the new value (redo) and the old value (undo) — and recovery is two passes, not one: redo to restore winners' lost changes, undo to erase losers' surviving ones. This is the answer forming to the opener: the extra information is the before-image, and it has to live in the log, forced ahead of the change just like the after-image, so that after a crash the database can always find what to roll back to.

58.2 Steal and no-force: the policy space that decides redo and undo

Whether recovery needs redo, undo, both, or neither is not arbitrary — it is fixed by two independent buffer-pool policy choices, a taxonomy owed to Härder and Reuter (1983). The first choice: may the buffer pool write a page dirtied by a still-uncommitted transaction back to disk? If yes, the policy is steal (a frame can be “stolen” from an uncommitted transaction and reused); if no, no-steal (dirty pages are pinned in memory until their transaction commits). The second choice: must all of a transaction's changes be forced to disk at commit? If yes, the policy is force; if no — Chapter 57's answer — no-force (commit forces only the log, and data pages drift to disk lazily). Each choice pins one recovery need. Steal implies undo: if an uncommitted change can reach disk, a crash can leave that change durable with its transaction unfinished, so recovery must be able to roll it back. No-force implies redo: if a committed transaction's data pages need not be on disk at commit, a crash can lose a committed change from memory, so recovery must be able to re-apply it. The two mirror the two threats of Chapter 57.1 — inconsistency from surviving uncommitted work (undo's job) and lost committed work (redo's job).

Laid out as a matrix (Figure 58.1), the four combinations demand different recovery machinery. No-steal + force needs neither redo nor undo — no uncommitted change ever reaches disk (nothing to undo) and every committed change is on disk at commit (nothing to redo) — but it is the policy Chapter 57 already ruled out: forcing scattered data on every commit caps throughput at the random-write rate (~19 MB/s), and pinning every dirty page until commit strangles the buffer pool, unable to evict anything a long transaction is holding. Relaxing either constraint buys performance at the price of a recovery obligation. The design every serious engine actually chooses — and the one ARIES is built for — is the most permissive corner, steal + no-force: the buffer pool evicts freely (great memory behavior) and commit forces only the log (great commit throughput), and the bill is that recovery must implement both redo and undo. That is why this chapter needs both, and why the before-image and after-image both go in the log. This is the answer to the opener and the quick check: because the engine chose steal, an uncommitted change can be on disk, so recovery keeps the before-image in the log to undo it; redo can never do that job because redo only re-applies, and re-applying the loser's change is the opposite of removing it.

(Answer to the §58.1 quick check: a loser is a transaction active at the crash that never committed; a winner is one that committed. A winner needs redo — re-apply its changes in case they were lost from memory; a loser needs undo — remove its changes in case they reached disk. Redo cannot substitute for undo because redo only re-applies a change, and the loser's change must be erased, which requires the old value the change overwrote.)

The same idea three ways: log the before-image and the after-image; redo winners, undo losers

1. In words. Because the engine steals (uncommitted changes may reach disk) and does not force (committed changes may not), recovery must both re-apply committed changes that were lost and roll back uncommitted changes that survived. So every log record carries both the new value (redo) and the old value (undo); recovery redoes to restore, then undoes to erase.

2. As a picture. Figure 58.1: a 2×2 matrix, steal/no-steal against force/no-force. Each cell is labelled with the recovery it needs — neither, redo only, undo only, or both. The steal + no-force cell (both) is highlighted: the corner every real engine chooses, the corner this book builds.

3. As numbers. The store logs 4 update records across two transactions; one commits, one (a loser) does not. After a crash, the redo pass re-applies 2 records and skips 2 already on their page (by LSN), and the undo pass reverses the loser's 2 updates; the recovered state equals the committed-only state exactly — True (§58.3).

58.3 A store that logs both: rolling back a loser after a crash

The working store makes redo and undo concrete under steal + no-force. It keeps data in pages; each change appends a log record carrying the page, key, before-image (undo), and after-image (redo), and — following the write-ahead rule — the record is logged before the page is touched. Two transactions run: T1 writes P1.a=1 and P2.c=5 and commits; T2 writes P1.a=99 and P2.z=7 and then the machine crashes before T2 commits. To exercise both recovery passes, the durable state at the crash is chosen to mirror what a real buffer pool would leave: page P1 was stolen to disk after T2's write (so on disk P1.a=99, an uncommitted value that must be undone), while page P2 was never flushed (so T1's committed P2.c=5 is lost from memory and must be redone). Recovery runs analysis to find the loser, a redo pass to repeat history, and an undo pass to roll the loser back:

redo + undo, the LSN and the page LSN
  log records: 4   committed txns: ['T1']
  on-disk P1 after STEAL (holds uncommitted T2 a=99): {'a': 99}
  loser transactions (no commit, must be undone): ['T2']
  redo pass: applied 2, skipped-as-already-present 2
  undo pass: reversed 2 loser updates
  recovered live cells: {('P1', 'a'): 1, ('P2', 'c'): 5}
  expected (committed-only): {('P1', 'a'): 1, ('P2', 'c'): 5}
  recovery == committed-only state: True
  second redo pass re-applies: 0 records (idempotent)

Read the two passes in order. Redo re-applies every logged change whose LSN is greater than its page's page LSN — repeating history so that any change missing from disk is restored. Here it applies 2: T1's P2.c=5 (a committed change lost with the unflushed page — precisely what no-force forces recovery to redo) and, notably, T2's P2.z=7, a loser's change that was also lost. Redo repeats all history, winners and losers alike, before undo sorts them out — an ARIES idea we return to in Chapter 60. It skips 2: the changes already on page P1, whose page LSN already covers them, so re-applying would be wasted work (and, as §58.4 shows, the skip is what makes redo safe to repeat). Undo then walks the loser T2's changes in reverse and restores each before-image: P1.a back to 1 (erasing the stolen 99) and P2.z back to nothing (deleting the insert) — 2 updates reversed. The result is exactly the committed-only state, P1.a=1, P2.c=5 — True: T1's work survived in full, T2's vanished without trace, atomicity and durability both kept. And the final line previews §58.4: run redo again on the recovered pages and it re-applies 0 records, because every change is now covered by its page LSN — recovery is idempotent, safe to run twice.

Trap: undo without a before-image, or applying the change before logging it

The two commonest ways to break undo are to not have the information it needs, or to have it too late. First, the missing before-image: a tempting “optimization” is to log only the new value (redo) — it is smaller, and Chapter 57's store did exactly that. But under steal, a loser's change can be on disk, and rolling it back requires the value the page held before the change; a redo-only log simply does not contain it, so the uncommitted write can never be removed and atomicity is lost the first time a stolen page belongs to an aborted transaction. A steal engine must log the before-image. Second, the undo-logging rule: the before-image must reach the log before the change reaches the data page on disk — the same write-ahead ordering as redo, and for a symmetric reason. If a data page carrying an uncommitted change were flushed before its undo record was durable, a crash in between would leave a change on disk with no logged before-image to reverse it to — an unrecoverable, unrollbackable state, the exact inconsistency of Chapter 57.1. Third, a subtler one: undo is not “write the old value back and forget it.” If recovery crashes during undo and a naive re-run simply re-undoes from scratch, it may try to roll back changes it already rolled back, or roll back past a value another action depends on. Real undo logs its own progress so it can resume, not restart — the compensation-log-record idea of Chapter 60. The honest posture: under steal you owe a before-image, logged ahead of the change, and an undo that records what it has already reversed — anything less is a rollback that works in tests and corrupts under a crash mid-recovery.

Say it like a systems engineer

Try it first. A teammate proposes: “Our log records are twice as big as they need to be because we store the old value and the new value for every update. Let's drop the old value — recovery just replays the log to rebuild state, so the new value is all we ever need.” Cover the paragraph and answer in four or five sentences, drawing on §58.1–§58.3.

Model answer. “The old value isn't redundant — it's the undo information, and we need it precisely because we steal. Our buffer pool evicts dirty pages without knowing whether their transaction has committed, so an uncommitted change can land on disk; if that transaction then aborts or we crash before it commits, atomicity says its change must disappear, and removing it means restoring the value the page held before — the old value we'd be dropping. Redo can't do that job: replaying the log re-applies the change, the opposite of erasing it. So a redo-only log is fine only under no-steal, where uncommitted changes never reach disk; the moment we steal — and we do, for buffer-pool performance — we owe both images. If log size is the worry, the answer is compression or physiological logging, not throwing away the before-image.” Naming steal, undo, and the atomicity obligation is the senior register.

58.4 The log sequence number: making redo idempotent and recovery restartable

One number underpins the whole scheme: the log sequence number (LSN), a monotonically increasing identifier assigned to every log record as it is appended. Because it only ever grows, an LSN doubles as a position in the log and a timestamp of relative order — record 500 happened before record 501 — and that lets recovery answer the question that makes redo safe: is this logged change already reflected on its data page? The trick is to store, on each data page, the LSN of the most recent log record applied to it — the page LSN — and to write it to disk with the page. Now recovery has a per-page high-water mark. During redo it compares each log record's LSN against the page LSN of the page it targets: if the record's LSN is less than or equal to the page LSN, the change is already on the page (the page was flushed after that change), so recovery skips it; only records newer than the page LSN are re-applied. This is exactly the “skipped 2” and the “second redo re-applies 0” of §58.3. The consequence is idempotence: applying the redo pass once or ten times reaches the same state, because after the first application every record is at or below its page LSN and every subsequent pass skips it.

Idempotence is not a nicety; it is what makes recovery correct at all, because recovery can itself be interrupted. A crash can strike during recovery — the power is no more reliable while the database is recovering than while it is running — and the only way a second recovery attempt can be safe is if re-applying already-applied changes is a no-op. Without the page LSN, redo would have no way to tell an already-applied change from a missing one; it would blindly re-apply, and a change that is not idempotent on its own (an increment, an append, a structural pointer update) would be corrupted by the second application. The page LSN turns “replay the log” from a fragile one-shot into a repeatable operation, which is the property Chapter 60 leans on completely: ARIES redoes all history on every recovery, however many times recovery restarts, and the page LSN is what keeps that safe. Two rules, then, carry forward: the LSN orders the log and stamps each page so redo knows what to skip; and recovery, being interruptible, must be idempotent — which the page LSN delivers for redo and which, for undo, will require the compensation records of Chapter 60. Correct because ordered and skippable; safe because repeatable.

58.5 What to carry forward

Work comes in transactions — atomic, bracketed by begin and commit/abort — which splits recovery's job in two: committed winners need redo (re-apply changes lost from memory), and uncommitted losers need undo (erase changes that reached disk), so the log must carry both a before-image and an after-image per change (§58.1). Which of redo and undo you owe is fixed by two buffer policies (Härder & Reuter 1983): steal (evict uncommitted dirty pages) forces undo, no-force (commit forces only the log) forces redo, and every real engine picks steal + no-force — best buffer and commit behavior — so it owes both (§58.2). A store logging both images lost a committed change and gained a stolen uncommitted one; recovery redid 2 changes (repeating all history), skipped 2 already on their page, and undid the loser's 2, landing exactly on the committed-only state (§58.3). The log sequence number orders the log, and its on-page copy, the page LSN, lets redo skip changes already durable — making redo idempotent and recovery safe to restart, which matters because a crash can strike during recovery (§58.4). The named trap: a redo-only log under steal cannot roll back, and an undo that restarts rather than resumes corrupts on a mid-recovery crash.

Two loose ends drive the rest of the part. First, §58.3's recovery still scanned the log from the very beginning to find winners, losers, and lost changes — fine for four records, impossible for a log that has grown for months. The fix is the checkpoint: a periodic record of which transactions are active and which pages are dirty, letting recovery start its scan near the end of the log instead of at record one — Chapter 59. Second, this chapter's undo simply overwrote before-images and, as the trap warned, a crash during undo would leave it unable to resume cleanly; and analysis, redo, and undo were sketched as three separate loops rather than one disciplined protocol. The algorithm that unifies all of it — a checkpoint-anchored analysis pass, a redo pass that repeats history using the page LSN, and an undo pass that logs compensation records so undo is itself redoable and restartable — is ARIES (Mohan et al. 1992), the subject of Chapter 60. Redo, undo, and the LSN are its three ingredients; the next two chapters assemble them into a recovery method that is correct even when the crash lands in the middle of recovery.
