Chapter 63 — The Transaction Concept: ACID, Isolation, and Anomalies

Before you start: Chapter 57 (write-ahead logging and the durability contract — the D of ACID, built), Chapter 60 (ARIES — atomicity and durability across a crash; its full name promised isolation too), Chapter 62 (the recovery capstone — durability complete, and the note that it only ever concerned one writer).  ·  Part X kept a database's word to a single writer across every failure. It said nothing about what happens when many transactions run at once and can observe each other's half-finished work. These anomalies, and the isolation levels that trade them away for concurrency, are the subject the rest of the part implements.

A transaction is a unit of work a database treats as indivisible, and Jim Gray's 1981 paper named the concept and its guarantees. Härder and Reuter's 1983 acronym ACID gives the four: Atomicity — all of a transaction's changes take effect or none do, no partial state survives (Chapter 60's undo). Consistency — a transaction moves the database from one state satisfying its invariants to another that also does; the application defines the invariants, and the transaction promises not to break them. Isolation — concurrent transactions do not see each other's uncommitted, in-progress state; each runs as if alone. Durability — once committed, a transaction's changes survive any failure (all of Part X). Part X delivered A and D end to end. This chapter is about I — the property that, unlike the others, is fundamentally about concurrency, and the one that recovery never touched. When transactions run one at a time, isolation is free. The instant they overlap, a scheduler that interleaves their reads and writes can produce results no serial order ever would — the anomalies. This chapter defines the transaction and ACID (§63.1); shows why concurrency needs control at all, with the lost-update interleaving (§63.2); walks the four classic anomalies on a running scheduler (§63.3); and lays out the isolation levels — the ANSI ladder as refined by Berenson et al. 1995 — each forbidding one more anomaly at the cost of concurrency (§63.4). By the end you can name what can go wrong and how much a given isolation level actually prevents — the vocabulary the rest of the part uses to build 2PL, MVCC, and optimistic concurrency control.

On the code in this chapter. One Python program (CPython 3.10.12 on this machine's 12th Gen Intel Core i7-12700H) that is a structural scheduler demonstration, not a real database. It encodes four explicit interleaved schedules over a tiny in-memory store — one per anomaly — and for each reports the value a transaction observed against the correct, serial-equivalent value, so the anomaly shows up as a mismatch. Phantom: the same predicate sums 120 then 150 after an insert. It then prints the ANSI isolation ladder as refined by Berenson et al. 1995. Each result is deterministic — a fixed schedule either exhibits the anomaly or it does not, and each does — so this is a structural demonstration of how interleavings misbehave, not a timing or a claim about any particular engine's defaults.

63.1 The transaction: ACID and the all-or-nothing contract

A transaction is the database's unit of agreement with the application: a group of reads and writes that must be treated as one indivisible action, however many individual operations it contains. The canonical example is a transfer — debit one account, credit another — which must happen fully or not at all; a state where the debit landed but the credit did not is not a slow transaction, it is money destroyed. Gray's 1981 “transaction concept” formalized this: the transaction is the boundary at which a database makes its guarantees, and those guarantees are the four letters of ACID (Härder & Reuter 1983). Atomicity and Durability are the two Part X built: atomicity says a crash or abort leaves no partial transaction (undo erases the losers), durability says a commit survives any crash (the WAL and ARIES). Consistency is the application's contract — the transaction, if run alone on a valid state, leaves a valid state — and the database's job is to preserve it under the other three properties. Isolation is the new one: it says concurrent transactions must not see one another's uncommitted work; each must behave as though it had the database to itself.

Isolation is different in kind from the others, and the difference is why it takes a whole part. Atomicity, consistency, and durability are properties of one transaction against failure; isolation is a property of many transactions against each other. Run transactions strictly one at a time — a serial schedule — and isolation is automatic and free: no transaction can see another's in-progress state because no other is in progress. But serial execution wastes a machine that can do many things at once, so real databases interleave transactions, running each a little at a time. Interleaving is where the performance lives and where the danger lives, because a scheduler that mixes one transaction's reads and writes with another's can produce outcomes that no serial order could — the anomalies. The gold standard isolation aims at is serializability: an interleaved schedule is acceptable if its effect equals some serial order of the same transactions. Anything less admits some anomaly. The rest of this chapter is about what those anomalies are and how much a given level of isolation gives up to avoid them; the rest of the part is about the mechanisms — locking, versioning, validation — that enforce a chosen level.

63.2 Why concurrency needs control: the interleaving that goes wrong

To see why isolation needs enforcing, watch the simplest interleaving break the simplest invariant. Two transactions each perform a read-modify-write on the same balance: read it, add an amount, write it back. Run serially, the effects add up — 100, then 110, then 130. Interleaved so that both read before either writes, one write silently overwrites the other. This is the opener, and the program's lost update line is exactly it:

Anomaly              observed        vs correct/serial   anomaly?
  lost update        x = 120          serial 130           True

Trace it. Balance starts at 100. Transaction T1 reads 100; transaction T2 also reads 100 — both captured the same starting value before either wrote. T1 computes 100+10 and writes 110; T2 computes 100+20 (against the 100 it read, not T1's 110) and writes 120. T1's update is gone — overwritten by a transaction that never saw it. A serial run would have reached 130 (100, then +10, then +20); the interleaving reached 120. Ten units of money vanished, with no crash, no error, no violated constraint the database could see — every individual operation was legal, and durability preserved every write that was made. This is the crux: recovery cannot save you here, because nothing failed. Both transactions committed; the log is perfectly consistent with what ran; ARIES would reproduce exactly this wrong answer. The bug is not in any single transaction and not in any failure — it is in the interleaving, and the only thing that prevents it is a concurrency-control mechanism that stops T2 from acting on a value T1 was about to change (or detects the conflict and aborts one of them). This is why isolation is a first-class problem: correctness under concurrency is not a property recovery provides or the application can easily code around; it must be enforced by the database's scheduler.

(Answer to the §63.1 quick check: the four ACID properties are Atomicity — all or nothing; Consistency — invariants preserved; Isolation — concurrent transactions do not see each other's uncommitted state; Durability — commits survive failure. Part X built Atomicity and Durability. Isolation is different in kind because it is a property of many transactions against each other, not of one transaction against failure — so it is automatic under serial execution and must be actively enforced the moment transactions interleave.)

Trap: the isolation level that felt strong enough — the lost update READ COMMITTED lets through

The comfortable assumption is that setting a database to READ COMMITTED — the default in many engines — makes concurrent updates safe, because “we only ever read committed data.” It does prevent the dirty read: you will never see another transaction's uncommitted value. But it does nothing for the lost update above. Both transactions read a committed 100, both compute against it, and the second write clobbers the first — every value read was committed, so READ COMMITTED is satisfied, and the money still disappears. The same level also permits non-repeatable reads and phantoms. The trap is reading the level's name as a guarantee of correctness rather than as the precise, narrow thing it is: READ COMMITTED forbids exactly one anomaly (dirty reads) and leaves the other three. The fixes are to raise isolation to a level that forbids the anomaly you actually face — REPEATABLE READ or SERIALIZABLE for the lost update — or to make the update atomic at the database (a single UPDATE accounts SET bal = bal + 10 that reads and writes under one lock, rather than a read in the application followed by a write). What you must not do is assume a level protects against an anomaly it does not name. Every isolation level is a specific set of anomalies forbidden and a specific set permitted; treating “committed” as a synonym for “correct” is how a lost update ships to production and is discovered only when the numbers stop adding up.

63.3 The four anomalies: dirty read, lost update, non-repeatable read, phantom

There are four classic anomalies, and each is a specific way an interleaving lets one transaction observe another's activity that a serial order never would. The program produces all four, each as a mismatch between what a transaction observed and the correct value:

Anomaly              observed        vs correct/serial   anomaly?
  dirty read         read 50          committed 100        True
  lost update        x = 120          serial 130           True
  non-repeatable rd  100 then 200      same row            True
  phantom            SUM 120 then 150   same predicate      True

Take them in turn. A dirty read is reading another transaction's uncommitted value. Here T1 withdraws 50, dropping the balance to 50 in its uncommitted workspace; T2 reads that 50; then T1 aborts and the balance rolls back to 100. T2 acted on a value that never truly existed — read 50 against a committed 100. A lost update (§63.2) is two read-modify-writes where one overwrites the other: 120 where a serial run reaches 130. A non-repeatable read is reading the same row twice and getting different values because another transaction committed a change in between: T1 reads x=100, T2 updates it to 200 and commits, T1 reads x=200 — the row it already read changed underneath it, so a computation depending on x reading the same value twice is broken. A phantom is the same anomaly for a set defined by a predicate rather than a single row: T1 runs SUM(amt) WHERE acct='A' and gets 120; T2 inserts a new row that also matches acct='A' and commits; T1 re-runs the same query and gets 150. No row T1 read changed — the difference is a new row that appeared, a phantom, matching a predicate T1 thought it had already answered. The distinction between the non-repeatable read and the phantom is exactly the distinction between an update to an existing row and an insert of a new one, and it matters because they need different mechanisms to prevent: locking the rows you read stops non-repeatable reads, but you cannot lock a row that does not exist yet, so stopping phantoms needs locking the predicate (or a range), which is why phantoms are the hardest of the four and the reason predicate locks (Eswaran et al. 1976) were invented. Four anomalies, four ways an interleaving betrays a transaction that assumed it ran alone.

The same idea three ways: four anomalies, one cause — uncontrolled interleaving

1. In words. Dirty read: seeing uncommitted data that may roll back. Lost update: two read-modify-writes, one overwrites the other. Non-repeatable read: the same row read twice returns different committed values. Phantom: the same predicate query returns a different set because a row was inserted. All four come from interleaving reads and writes of transactions that each assumed they ran alone.

2. As a picture. Figure 63.1: four two-lane timelines, T1 above and T2 below. Dirty read: T2's read arrow crosses into T1's uncommitted region before T1's abort. Lost update: both read arrows precede both write arrows; T2's write lands on top. Non-repeatable read: T1's two reads bracket T2's committed write. Phantom: T1's two queries bracket T2's insert of a new matching row (drawn as a fresh box appearing between the reads).

3. As numbers. Dirty read: observed 50 vs committed 100. Lost update: 120 vs serial 130. Non-repeatable read: 100 then 200 on the same row. Phantom: SUM 120 then 150 on the same predicate. Each is a mismatch between what a transaction saw and what a serial order would have given (§63.2–§63.3).

63.4 Isolation levels: the ANSI ladder and what each forbids

Since preventing every anomaly costs concurrency, the SQL standard offers a ladder of isolation levels, each forbidding one more anomaly than the last, so an application can buy exactly the correctness it needs and no more. The program prints the ladder, as refined by Berenson et al. 1995:

Isolation ladder (ANSI, as refined by Berenson et al. 1995): each level forbids one more.
  READ UNCOMMITTED forbids: none of the below
  READ COMMITTED   forbids: dirty read
  REPEATABLE READ  forbids: dirty read, non-repeatable read, lost update
  SERIALIZABLE     forbids: dirty read, non-repeatable read, lost update, phantom

Read the ladder from the bottom. READ UNCOMMITTED forbids none of the four — it permits even dirty reads, trading all isolation for maximum concurrency, useful only for approximate, read-only reporting where a transient wrong value is tolerable. READ COMMITTED forbids the dirty read: you never see uncommitted data, but the same row can still change between two reads (non-repeatable), a set can still grow (phantom), and updates can still be lost — this is the default in many engines and the source of the §63.2 trap. REPEATABLE READ additionally forbids the non-repeatable read (and, in Berenson et al.'s refinement, the lost update): rows you have read stay stable for your transaction's life, but new rows matching a predicate can still appear, so phantoms remain. SERIALIZABLE forbids all four, including the phantom: the execution is equivalent to some serial order, the correctness gold standard of §63.1 — and the most expensive, because preventing phantoms means locking predicates or ranges, not just rows. The ANSI standard originally defined the levels by three phenomena (dirty read, non-repeatable read, phantom); Berenson et al. 1995 showed those definitions were ambiguous and incomplete — missing the lost update and mis-specifying the levels under real locking — and refined them, which is why this book states the ladder in their corrected form. The practical reading is the one the trap insisted on: an isolation level is a precise set of anomalies forbidden, not a vague strength rating, and choosing one is choosing exactly which anomalies you can tolerate in exchange for how much concurrency. The mechanisms that enforce these levels — two-phase locking, multiversion concurrency control, optimistic validation — are the subject of the chapters that follow; this chapter gives you the anomalies they exist to prevent and the ladder that names how far to go.

Say it like a systems engineer

Try it first. A teammate reports a bug: “Our balance-update endpoint occasionally loses an increment under load. We're on READ COMMITTED, which the docs say means we only read committed data — so how is an update getting lost? Committed reads should be safe.” Cover the paragraph and answer in four or five sentences, drawing on §63.2 and §63.4.

Model answer. “READ COMMITTED does exactly one thing: it stops you reading uncommitted data. It does not stop a lost update. Two requests each read a committed balance, each add their increment to the value they read, and the second write overwrites the first — every read was committed, so the level is satisfied, and an increment still vanishes. The name protects against dirty reads, not against concurrent read-modify-write. Two real fixes: raise isolation to REPEATABLE READ or SERIALIZABLE, which forbid the lost update, or — better and cheaper — make the update atomic in the database with UPDATE accounts SET bal = bal + :n so the read and write happen under one lock instead of reading in the app and writing back later. What we can't do is treat ‘committed’ as ‘correct’; each isolation level forbids a specific list of anomalies, and this one isn't on READ COMMITTED's list.” Naming the anomaly, what the level actually forbids, and the atomic-update fix is the senior register.

63.5 What to carry forward

A transaction is a database's indivisible unit of work (Gray 1981), and its contract is ACID (Härder & Reuter 1983): Atomicity (all or nothing), Consistency (invariants preserved), Isolation (concurrent transactions do not see each other's uncommitted state), Durability (commits survive failure). Part X built A and D; Part XI is about I, which is different in kind — a property of many transactions against each other, free under serial execution but requiring active enforcement the moment they interleave (§63.1). Uncontrolled interleaving produces anomalies that no serial order would, and recovery cannot help because nothing failed — the lost update reaches 120 where a serial run reaches 130, and both transactions committed cleanly (§63.2). The four classic anomalies are the dirty read (uncommitted data, later rolled back: read 50 vs committed 100), the lost update (one write overwrites another), the non-repeatable read (a row changes between two reads: 100 then 200), and the phantom (a set grows between two predicate queries: SUM 120 then 150) — the last hardest because you cannot lock a row that does not yet exist (§63.3). The isolation levels form a ladder, each forbidding one more anomaly at the cost of concurrency: READ UNCOMMITTED (none), READ COMMITTED (dirty read), REPEATABLE READ (also non-repeatable read and lost update), SERIALIZABLE (also phantom), stated in Berenson et al.'s 1995 corrected form (§63.4). The named trap: reading an isolation level's name as a guarantee of correctness rather than the specific, narrow set of anomalies it forbids — READ COMMITTED still permits the lost update.

This chapter is the vocabulary the rest of Part XI speaks. You now know what a transaction promises, what goes wrong when transactions overlap without control, and how the isolation levels name a chosen point on the correctness/concurrency trade. What you do not yet have is any mechanism that enforces a level — so far the anomalies are just described, and the ladder is just a specification. The chapters ahead build the enforcement. First comes the theory that makes “equivalent to some serial order” precise and checkable — serializability and the conflict graph — so a scheduler can decide whether an interleaving is safe. Then come the three mechanisms real systems use to guarantee it: two-phase locking, which makes transactions acquire and release locks in a disciplined order (its foundations in Eswaran et al. 1976); multiversion concurrency control, which lets readers see a consistent snapshot without blocking writers; and optimistic concurrency control, which runs transactions freely and validates at commit. Each enforces isolation a different way, with a different cost profile, and each is the answer to the question this chapter only posed: given that interleaving can corrupt, how does a database interleave safely? The anomalies you can now name are exactly what those mechanisms exist to prevent.
