Chapter 52 — Solutions

52.1 Borrowing moves one key from a sibling that has a spare, rotating it through the parent separator, and leaves the tree's structure unchanged; merging fuses the under-full node with a sibling into one node and pulls the parent's separator key down between them, destroying a node. Tempting wrong answer: “borrow moves a key directly between siblings” — it must pass through the parent, because the separator has to stay between the two children. Feed-forward: §52.1.
52.2 It shrinks at the root: when a merge propagates all the way up and empties the root, the root is removed and its single remaining child becomes the new root, dropping the height by one. Tempting wrong answer: “the tree shrinks by making a leaf shallower” — leaves never change depth individually; height changes only at the root, symmetric with growth. Feed-forward: §52.1.
52.3 About 69% full — the constant ln 2 ≈ 0.693 (Yao 1978, measured here at 0.684–0.687). An index built by insertion carries about 1/ln 2 ≈ 1.44× the pages of the same keys bulk-loaded — roughly 44% more. Tempting wrong answer: “about 100% full” — that is bulk-loading; naive 50/50 splits leave nodes averaging ln 2. Feed-forward: §52.3.
52.4 (a) A merge destroys a node (fusing two into one) and pulls a key down from the parent to sit between them — the exact reverse of a split, which creates a node and pushes a key up. (b) Pulling the separator down removes a key from the parent, which may itself drop below the minimum and merge, and so on up the tree. (c) The height decreases only when the merge reaches the root and leaves it with no keys and one child: that child becomes the new root. Because a whole level is removed uniformly at the top, every leaf loses the same one level, so all leaves stay at the same depth. Tempting wrong answer: “a merge anywhere lowers the height” — only a root-emptying merge does; internal merges just reduce a parent's key count. Feed-forward: §52.1.
52.5 (a) An eager merge locks three pages at once — the under-full node, its sibling, and the parent — and may propagate and lock more, which is heavy contention to spend on the common case where the slot is soon refilled; so engines defer it. (b) Index bloat is the index keeping its page count as live keys fall: occupancy drops toward the deleted fraction and range scans still walk the mostly-empty pages, paying fetches for absent keys. (c) A rebuild (REINDEX, or drop-and-recreate) reclaims the space; it is denser because it bulk-loads the surviving keys bottom-up, packing nodes to ~100% rather than leaving the under-full pages the deletes created. Tempting wrong answer: “lazy deletion is a bug” — it is a deliberate space-for-concurrency trade. Feed-forward: §52.2.
52.6 (a) About 69% (ln 2), implying a size ratio 1/ln 2 ≈ 1.44. (b) Roughly 1,440,000 pages — about 44% more than the 1,000,000 packed pages. (c) The extra pages cost more buffer-pool space (fewer of the index's pages stay resident, so more look-ups miss to disk) and, because lower occupancy means lower effective fanout, the tree can be a level taller, adding a page fetch to some look-ups. Tempting wrong answer: “the extra pages only waste disk” — they also cost cache residency and can add height. Feed-forward: §52.3.
52.7 (a) At most two at any moment — the current node and its parent — released as the search moves down; that is enough because crabbing never lets go of the parent until the child is safely latched, so no concurrent change can move a node out from under the descent. (b) It may hold the entire root-to-leaf path (up to the height) latched; it can release the ancestors only once it reaches a node that is safe — has room, so a change there cannot push a split upward. (c) When nodes are near-full, almost no node on the path is “safe,” so ancestor latches (including the root's) are held for the whole descent, and inserts serialize on the root. Tempting wrong answer: “a read also holds the whole path” — a read holds only one or two latches; it is the insert's split-safety that forces path-long holds. Feed-forward: §52.4.
52.8 Step 4: The search compares its target to the leaf's recorded high key, sees the target now exceeds it, and follows the right-link to the new sibling that the split created — where its key now lives — and continues there. Because any downward move a split makes can be recovered by moving right, the search never needed the parent latch to protect against a split below it; the right-link makes the split locally recoverable, so one latch at a time suffices. Tempting wrong answer: “it must restart from the root” — the right-link lets it move sideways to the sibling without re-descending. Feed-forward: §52.4.
52.9 (a) Lazy deletion — under-full pages are tolerated, not merged, so the page count holds. (b) Bulk-loading — the rebuild packs nodes to ~100% versus ln 2. (c) Borrow — a single key moved from a sibling, no structural change. (d) Merge — the only operation that can lower height, when it empties the root. (e) The right-link — the search follows it sideways after a concurrent split. Tempting wrong answer: attributing (b) to borrow or merge — density comes from bulk-loading the survivors, not from rebalancing. Feed-forward: §52.1–§52.4.
52.10 (a) True — height decreases only when a merge propagates to and empties the root. (b) False — random insertion averages ln 2 ≈ 69%, not 85%. (c) True — building bottom-up from sorted data fills each node and never splits, so it packs to ~100%. (d) False — deletion is usually lazy, leaving under-full pages; the index shrinks only on a rebuild. (e) False — the right-link's whole point is that a search holds only one latch and recovers a split by moving right, needing no parent latch. Tempting wrong answer: marking (d) true because “deletes free space” — they free logical entries, not on-disk pages, until a rebuild. Feed-forward: §52.1–§52.4.
52.11 (a) Insert: descend, and if the node is full, create a new node, move half the keys to it, push a separator up — propagating up, growing at the root. Delete: descend, and if the node underflows, merge with a sibling, move its keys in, pull a separator down — propagating up, shrinking at the root. Each step of one reverses a step of the other. (b) In practice the split is unavoidable (an over-full node cannot hold its keys) but an under-full node is still correct to read and search, so the merge can be safely skipped; deferring it avoids the three-page lock, breaking the symmetry for performance. (c) Insertion alone only reaches ln 2 occupancy, and deferred merges leave deleted pages under-full, so a long-lived tree drifts to ever-lower density; periodic rebuilds (or online reorganization) counter the drift by repacking. Tempting wrong answer: “the merge is skipped because it is incorrect” — it is correct but costly; it is skipped for concurrency, not correctness. Feed-forward: §52.1–§52.3.
52.12 Open-ended and platform-specific. A correct write-up: (a) implements a minimum-degree t B-tree with split on insert and borrow/merge on delete; (b) inserts a seeded random key order and reports average node occupancy converging on ln 2 ≈ 0.693 across a few t (this chapter measured 0.684–0.687 at t = 16, 32, 64); (c) deletes most keys and shows the height shrinking with all survivors still found; (d) states toolchain and notes occupancy and height are structural results of a deterministic operation sequence — reproducible and hardware-independent, not wall-clock timings. Tempting wrong answer: reporting occupancy or height as a performance number — both are structural properties of the tree's shape. Feed-forward: §52.3.
