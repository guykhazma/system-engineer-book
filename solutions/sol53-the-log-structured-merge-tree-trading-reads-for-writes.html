Chapter 53 — Solutions

53.1 The LSM-tree refuses to update pages in place; instead of finding a key's page and rewriting it (a random write), it buffers writes and flushes them sequentially. The Chapter 46 measurement that makes this pay is that sequential access (~916 MB/s) is about 49× faster than random 4 KiB access (~19 MB/s). Tempting wrong answer: “it avoids writing to disk” — it writes plenty, but only sequentially. Feed-forward: §53.1.
53.2 In order: the write-ahead log (WAL), then the memtable, then — when the memtable fills — the flushed SSTable. The WAL exists purely for durability: it is the sequential, fsync'd record that lets the in-memory memtable be rebuilt after a crash. Tempting wrong answer: naming the SSTable as the durability mechanism — the SSTable is the eventual sorted file; the WAL is what makes an in-RAM write survive a crash before the flush. Feed-forward: §53.2.
53.3 A delete writes a tombstone — a marker “this key is deleted” — into the memtable, which flushes like any other write. It cannot remove the key from disk because SSTables are immutable, so the old value still sits in older files; the tombstone, being newest, shadows it at read time. Tempting wrong answer: “it erases the key from the file” — immutability forbids that; deletion is by shadowing, not erasure. Feed-forward: §53.3.
53.4 (a) Appending in arrival order never seeks — every write is a pure sequential append, the fast side of the Chapter 46 gap. (b) A point read is catastrophic because the log is in arrival order, not key order, so the key could be anywhere and must be scanned for; and you cannot stop at the first match from the front, because a later append may hold a newer value, so the newest copy is whichever is last in the log. (c) Sortedness: keep the memtable sorted and flush it sorted, so each file is internally sorted — found by binary search in one file, and merged linearly across two like mergesort's merge step. Tempting wrong answer: “scan from the back and stop at the first match” — correct for finding the newest value but still a full-file scan per read; sortedness is what removes the scan. Feed-forward: §53.1–§53.2.
53.5 (a) The memtable, then the SSTables newest to oldest; newest must win because a later write shadows an earlier one, so the first source holding the key has its current value and older copies are superseded. (b) After put v2 (flush): read = v2. After put v3 (flush): read = v3 (the newer of two SSTables shadows v2). After delete (flush): read = None (the tombstone, newest, shadows v3 and v2, which still sit on disk). (c) A point miss must touch every source, because only after finding the key in none of them can it conclude absence — it can never stop early. Tempting wrong answer: “a hit is the worst case because it reads a value” — a hit can stop at the first source that has the key; a miss cannot stop at all. Feed-forward: §53.3.
53.6 (a) It keeps writes sequential (no file is ever randomly rewritten) and makes files safe to read concurrently and to cache, since nothing mutates under a reader. (b) An update just writes the new value into the memtable, which flushes to a newer SSTable; the newer copy shadows the old at read time. (c) Since the old value cannot be erased from its immutable file, deletion writes a tombstone that, being newest, shadows the old value instead. Tempting wrong answer: “immutability only helps concurrency” — its first purpose is keeping every write sequential. Feed-forward: §53.2–§53.3.
53.7 (a) The number of SSTables is the total writes divided by the flush threshold (roughly 100,000/1,000 ≈ 99 and 100,000/5,000 ≈ 19 in the model), since each threshold's worth of writes flushes one file. (b) A miss scans all of them (99, then 19); the miss is the worst case because it cannot stop at a first hit — the key is in none of the files, so every one must be probed. (c) A larger flush threshold means a larger memtable held in volatile RAM and more writes to replay from the WAL after a crash — more memory and slower recovery. Tempting wrong answer: “just make the threshold huge” — that trades read amplification for memory and crash-recovery time. Feed-forward: §53.3–§53.4.
53.8 Step 4: Each processed-and-deleted row left a tombstone, and every tombstone in the scanned range must be read and skipped, because each might be shadowing a live value in an older run — the scan cannot know without reading it. So a range that has churned through tens of thousands of insert/delete cycles holds tens of thousands of tombstones over its ~10 live rows, and the scan physically reads all of them to return almost nothing. It gets fast again only when a compaction merges the runs and drops the tombstones (and the values they shadow) from that range. Tempting wrong answer: “add an index on the range” — the cost is the tombstones themselves; only compaction removes them. Feed-forward: §53.3–§53.4.
53.9 (a) The WAL — a crash replays the log to rebuild the memtable, so no acknowledged write is lost. (b) Read amplification — a miss probes every file. (c) The tombstone — a deleted key's marker and its shadowed value occupy space until compaction. (d) The memtable — recent writes are served from RAM. (e) SSTable immutability — nothing mutates the file, so it needs no read lock. Tempting wrong answer: crediting (a) to the memtable — the memtable is volatile; it is the WAL that survives the crash. Feed-forward: §53.2–§53.4.
53.10 (a) False — even the flush is a sequential write; an LSM-tree issues no random writes. (b) False — a delete writes a tombstone and adds data; space is reclaimed only by compaction. (c) False — a read returns the value from the newest source that contains the key. (d) True — both the WAL append and the flush are sequential. (e) True — that is exactly read amplification. Tempting wrong answer: marking (a) true because “the flush goes to a specific place” — the flush is one large sequential write of a whole sorted file, not a random update. Feed-forward: §53.1–§53.4.
53.11 (a) Write cost: B-tree updates a leaf in place (random write, expensive) vs LSM appends sequentially (cheap). Read cost: B-tree descends one shallow tree (cheap) vs LSM merges many sorted runs (read amplification). Space: B-tree packs to ~69% and holds one copy vs LSM lets dead versions and tombstones linger until compaction (loose). (b) The LSM's write amplification comes from compaction re-reading and re-writing data that was already written; it is the counterpart to the B-tree's random-write cost, but it is deferred (paid later, in the background) and sequential (large merges), whereas the B-tree's is immediate and random (per insert). (c) B-tree is the right default for read- and range-scan-heavy workloads that update in place; the LSM-tree for write- and ingest-heavy workloads that can afford background merging and looser space. Tempting wrong answer: “the LSM has no write cost” — it defers the cost into compaction as write amplification. Feed-forward: §53.1–§53.5.
53.12 Open-ended and platform-specific. A correct write-up: (a) implements a sorted memtable that flushes to an immutable sorted SSTable at a threshold, a newest-to-oldest read, and a tombstone delete; (b) drives it with a seeded write stream over a small key space and reports the SSTable count (writes / threshold) and the files a point miss must scan; (c) verifies newest-write-wins and tombstone-shadows-value (this chapter's model: 99 and 19 SSTables at thresholds 1,000 and 5,000, a miss scanning all of them, get = v3 then None after the delete); (d) states toolchain and notes the file count and scan count are structural outcomes of the logic and the key stream — reproducible, not wall-clock timings. Tempting wrong answer: timing the reads and reporting milliseconds as the result — the reproducible quantities are the structural counts. Feed-forward: §53.3.
