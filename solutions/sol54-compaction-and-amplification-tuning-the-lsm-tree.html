Chapter 54 — Solutions

54.1 It reclaims superseded update versions (keeping only the newest value per key) and deleted data; a tombstone it meets is dropped along with the older values it was shadowing, since after the merge no older run remains to hide them. Tempting wrong answer: “it keeps the tombstone forever” — the tombstone is dropped once compaction has merged past every value it shadowed. Feed-forward: §54.1.
54.2 Write amplification (compaction rewrites data as it merges into larger runs), read amplification (a lookup probes several runs), and space amplification (dead versions and tombstones linger until compaction removes them). Tempting wrong answer: naming only write and read — space amplification is the third and the one size-tiered blows up most. Feed-forward: §54.2.
54.3 Leveled compaction minimizes read (and space) amplification by keeping one run per level; size-tiered minimizes write amplification by writing each byte about once per level. Tempting wrong answer: “leveled minimizes write amplification” — it is the opposite; leveled pays the most in writes. Feed-forward: §54.3.
54.4 (a) The keyspace was small (5,000) and the runs overlapped, so most of the 25,934 entries were superseded updates or tombstones of the same keys; only the newest live value of each surviving key remained — 3,362 entries. (b) It became 1× for that range: the merged output is a single run, so a read touches one file instead of twenty. (c) Compaction still read all 25,934 inputs and wrote 3,362 outputs; that rewriting of already-stored data is write amplification, the cost paid to lower read and space amplification. Tempting wrong answer: “compaction is free because it shrinks the data” — it shrinks stored data but spends write bandwidth to do it. Feed-forward: §54.1–§54.2.
54.5 (a) The RUM conjecture: optimizing any two of read overhead, update overhead, and memory/space overhead comes at the expense of the third. (b) Aggressive compaction merges runs promptly, so few runs and little dead data (low read and space) but constant rewriting (high write); lazy compaction merges rarely, so little rewriting (low write) but many runs and much dead data (high read and space). (c) Both engines face read/update/space; the B-tree spends it as immediate random writes and tight space, the LSM-tree as deferred sequential write amplification and looser space — same trilemma, different corner. Tempting wrong answer: “the LSM-tree escapes the trade the B-tree faced” — it relocates the trade, it does not escape it. Feed-forward: §54.2.
54.6 (a) Leveled keeps exactly one sorted run per level; size-tiered lets up to T runs accumulate per level and merges them together when the level fills. (b) Leveled: promoting data into a level that is T× bigger rewrites ~T bytes per byte, across L levels → ~T×L; size-tiered: each byte is written once per level (in the bulk merge) → ~L. (c) Leveled: at most one run per level, so a read checks ~L runs; size-tiered: up to T runs per level, so a read checks ~T×L. Tempting wrong answer: assuming both read and write scale the same way — they scale oppositely, which is the whole trade. Feed-forward: §54.3.
54.7 (a) Leveled — read amplification 3 and space 1.10 keep latency low and waste little of the expensive storage, at the cost of write amplification 30, which a read-critical index can afford. (b) Size-tiered — write amplification 3 spares the cheap disk's write bandwidth and wear, and the firehose can tolerate read amplification 30 and 10× space on cheap storage. (c) About 30 TB hit the device (30×1 TB); it matters because an SSD's endurance is finite writes, so 30× amplification burns through its rated lifetime ~30× faster. Tempting wrong answer: “pick leveled everywhere because low read amp is always best” — for the firehose its 30× write amplification is the dominant cost. Feed-forward: §54.3–§54.4.
54.8 Step 4: This is a write stall (write throttling). It appears exactly at peak write load because that is when ingest most outruns compaction: the top-level runs pile up faster than they can be merged, read amplification there climbs, and the engine throttles writes to keep it bounded — so the “fast writes” degrade precisely when they are busiest. Two levers: provision more compaction throughput (I/O bandwidth and threads) so merging keeps pace, and/or move to a compaction family with lower write amplification (size-tiered) so less merging is needed per byte — accepting its higher read and space cost. Tempting wrong answer: “add more memory to the memtable” — a bigger memtable delays but does not remove the stall; the bottleneck is compaction throughput versus ingest. Feed-forward: §54.4.
54.9 (a) Write amplification — the device physically writes several times the logical volume. (b) Space amplification — dead versions and tombstones inflate on-disk size well past live data. (c) Read amplification — many runs probed per level. (d) Leveled compaction — one run per level. (e) Size-tiered compaction — merges a level's runs when it fills. Tempting wrong answer: crediting (a) to read amplification — reads do not wear the device; writes do. Feed-forward: §54.2–§54.3.
54.10 (a) False — the RUM tension means no strategy makes all three small; you spend one to save another. (b) False — compaction merges sorted runs in one sequential pass, reading and writing sequentially. (c) True — size-tiered trades higher read and space for lower write amplification. (d) False — compaction contends for device bandwidth and buffer pool and can cause write stalls, affecting foreground latency. (e) True — levels ≈ log-base-T, so larger T means fewer levels. Tempting wrong answer: marking (d) true because “background” sounds free — it is real work on the same device. Feed-forward: §54.1–§54.4.
54.11 (a) B-tree: low read, high (random) write, low space (~69% fill) — one point. Leveled-LSM: low read, high write, low space — but write is deferred and sequential. Size-tiered-LSM: high read, low write, high space. Each coordinate follows from the mechanism (in-place update; one-run-per-level; many-runs-per-level). (b) By varying T and choosing the compaction family, the LSM-tree reaches many points along the read/write/space surface, whereas the B-tree's in-place discipline fixes it near one; that tunability lets high-ingest systems place their cost where they can afford it. (c) The best point depends on the workload's read/write/space sensitivity, and the RUM conjecture says no point is best on all three — so the answer is a function of the workload, not of the engine. Tempting wrong answer: “the LSM-tree is strictly better because it's tunable” — tunable means it can be set badly too; it is better only when the workload wants a corner the B-tree can't reach. Feed-forward: §54.2–§54.5.
54.12 Open-ended and platform-specific. A correct write-up: (a) implements a k-way merge keeping the newest value per key and dropping tombstones, reporting input and output counts and the reclaimed fraction (this chapter: 25,934 → 3,362, 87% reclaimed); (b) computes write/read/space amplification for leveled (~T×L / ~L / ~1) and size-tiered (~L / ~T×L / ~T) across a few T; (c) states toolchain and notes the reclaimed fraction is a structural outcome of the merge logic and the amplification figures are exact model arithmetic — reproducible and hardware-independent, neither a wall-clock timing. Tempting wrong answer: reporting the amplification numbers as measured device throughput — they are a model of the structure, not a benchmark. Feed-forward: §54.3.
