Chapter 55 — Solutions

55.1 On insert, it hashes the key with k functions and sets the k named bits to one; on test, it hashes the key the same way and answers “definitely not” if any of those bits is zero, “possibly” if all are one. Tempting wrong answer: “on test it returns yes/no” — it returns “definitely not” or “possibly,” never a confirmed yes. Feed-forward: §55.2.
55.2 It can make a false positive (say “possibly” about an absent key, because that key's bits were set by others) and can never make a false negative (insertion only sets bits, so a present key always has all k bits set). Tempting wrong answer: “it can miss a present key” — that is a false negative, which is impossible. Feed-forward: §55.2.
55.3 A hit usually resolves in the memtable or a recent run, so it stops early; a miss has nothing to short-circuit it and would otherwise probe every run, so the filter's “definitely not” is what removes those wasted probes. Tempting wrong answer: “the filter speeds up hits” — a present key still triggers the authoritative read; the win is on misses. Feed-forward: §55.1–§55.4.
55.4 (a) Insertion sets all k of a key's bits, so if any is still zero the key was never inserted — the proof of absence is exact. (b) All-ones can arise from other keys' bits overlapping this one's, so it does not prove insertion — only “possibly.” (c) The store is authoritative, so a “definitely not” skips a run correctly every time and a false “possibly” costs only one wasted probe the store then resolves; a false negative, by contrast, would skip a run that does hold the key and return a wrong “not found” — a correctness bug. Tempting wrong answer: “a false positive is the dangerous error” — a false positive only wastes a probe; the false negative (impossible here) is the one that breaks correctness. Feed-forward: §55.2.
55.5 (a) p ≈ (1 − e^(−kn/m)) raised to the k power. (b) The formula is an expectation; the 0.88% is one measured outcome over 100,000 probes, so it differs from 0.82% by ordinary sampling noise, not a wrong model. (c) Because the error decays exponentially in m/n, so a fixed additive increase in bits per key multiplies the error by a roughly constant factor rather than subtracting a constant. Tempting wrong answer: “the gap means the formula is wrong” — it is within sampling noise and the two track across two orders of magnitude. Feed-forward: §55.3.
55.6 (a) Optimal k* = (m/n) ln 2; bits per key m/n = −ln p / (ln 2) squared. (b) ~9.6 bits per key for 1%, which for a billion keys is about 1.2 GB. (c) The rule fixes bits per key, so total memory scales linearly with key count but the per-key budget for a given error rate is constant. Tempting wrong answer: “more keys need more bits per key” — more keys need more total bits, but the per-key budget for a target p is fixed. Feed-forward: §55.3.
55.7 (a) No filter: ~10 runs; 1% filter: ~0.1 runs; 0.1% filter: ~0.01 runs (expected probes = L×p). (b) A 1% filter removes about 99% of the miss read work — nearly all of it, since almost every miss now resolves in memory. (c) A range scan needs keys in an interval, but hashing destroys order, so the filter cannot say which runs hold keys in [a, b] and no run can be skipped. Tempting wrong answer: “the filter halves range-scan cost too” — it does nothing for ranges; it is a point-membership structure. Feed-forward: §55.4.
55.8 Step 4: This is a correctness bug, not a performance one. The misused promise is that “possibly present” is a confirmed membership — it is not; a Bloom filter has false positives, so ~1% of absent keys report “possibly” and the code then invents a value for a key that was never stored. The one-line rule: a filter guards the store and never replaces it — every “possibly” must still go to the authoritative read. Tempting wrong answer: “raise the bits per key to fix it” — a lower false-positive rate makes the bug rarer, not gone; only doing the real lookup on every hit is correct. Feed-forward: §55.3.
55.9 (a) False negative — the mistake it can never make. (b) False positive — the occasional wasted run probe. (c) Optimal k — fixed by the memory budget to minimize the error. (d) Range scan — the read it cannot accelerate. (e) Bits per element — the fixed per-key cost that sets the target rate. Tempting wrong answer: swapping (a) and (b) — absence is certain (no false negative), presence is a guess (false positive). Feed-forward: §55.2–§55.4.
55.10 (a) False — a filter can only say “possibly present,” never confirm presence. (b) True — insertion sets all k bits, so a present key is never rejected. (c) False — the error falls exponentially, so doubling bits per key cuts it by far more than half; adding a constant number of bits multiplies it by a constant factor. (d) False — clearing bits may clear ones another key needs, creating a false negative; use a counting or cuckoo filter to delete. (e) False — hashing destroys order, so a filter cannot skip runs for a range scan. Tempting wrong answer: marking (c) true because “more bits, less error” sounds linear — the relationship is exponential. Feed-forward: §55.2–§55.4.
55.11 (a) At each of the ten runs the read consults the filter; for a true miss each says “definitely not” except the 1% false-positive fraction, so in expectation about 10×0.01 = 0.1 runs are actually opened — roughly one device access every ten misses. (b) The filter removes almost all point-miss probes, bringing point-read amplification near the B-tree's ~1; but it summarizes only exact keys, so range scans still open every overlapping run and stay above the B-tree's clustered single scan. (c) Monkey: a lookup's expected cost is the sum of the per-run false-positive rates, so for a fixed total memory it is better to give more bits per key to the larger, more numerous lower levels and fewer to the small upper ones — minimizing the summed false-positive probability rather than equalizing bits per key. Tempting wrong answer: “filters close the range-scan gap too” — they close only the point-read gap. Feed-forward: §55.4.
55.12 Open-ended and platform-specific. A correct write-up: (a) implements a bit-array filter with k hash indices, inserts n keys, probes n absent keys, and reports the empirical false-positive rate at several bits-per-element budgets (this chapter: ~0.88% at 10 bits, k=7); (b) lays the closed-form (1 − e^(−kn/m))^k beside each measurement and finds them within sampling noise; (c) states toolchain and notes the false-positive rate is a hardware-independent function of k, m, n — a structural rate reproducible anywhere, differing from the formula only by sampling noise, not a wall-clock timing. Tempting wrong answer: reporting the false-positive rate as a device throughput measurement — it is a property of the structure, not a benchmark. Feed-forward: §55.3.
