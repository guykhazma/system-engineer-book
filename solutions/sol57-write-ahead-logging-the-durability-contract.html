Chapter 57 — Solutions

57.1 A crash erases volatile memory — the buffer pool's dirty pages and the LSM memtable — so any acknowledged write that lived only there is lost, breaking the promise the database made when it said “committed.” Tempting wrong answer: “nothing is lost because the data is on disk” — the whole point is that acknowledged writes are deferred and may not have reached disk yet. Feed-forward: §57.1.
57.2 Durability: once the database acknowledges a write as committed, that write survives any subsequent crash. Tempting wrong answer: “durability means the data is never lost” — it is specifically about acknowledged writes surviving a crash, not an absolute guarantee against all loss. Feed-forward: §57.2.
57.3 The log record describing a change must reach stable storage before the change reaches the data on disk (and before the commit is acknowledged). Tempting wrong answer: “the data must be written before the log” — that is backwards and defeats recovery. Feed-forward: §57.4.
57.4 (a) The force policy flushes the changed data all the way to disk with fsync before acknowledging, so an acknowledged write is truly durable — correct by construction. (b) It is slow because the data structure is large and its changed pages are scattered, so each commit does many small random writes (~19 MB/s) plus an expensive fsync, capping throughput at the random-write rate. (c) Forcing a small sequential log record instead makes the change durable at the cost of one append, and no-force means the data pages are written back lazily, later, because the log already guarantees their durability. Tempting wrong answer: “no-force means the data is never persisted” — it is persisted lazily, just not on the commit path. Feed-forward: §57.2.
57.5 (a) Its only copy of the data was the volatile in-memory map, which the crash erased, so with nothing durable to replay it recovered 0 keys. (b) The log preserved the exact order of operations, so replaying overwrites and deletes in that order lands on the same final value per key — 163 live keys. (c) It never wrote the data structure (the map) to disk at all; durability still held because every acknowledged change was preceded by a forced log record, and the log survived the crash. Tempting wrong answer: “recovery worked because the map was flushed periodically” — it was never flushed; the log alone restored the state. Feed-forward: §57.3.
57.6 (a) A crash between the data page hitting disk and its log record being forced leaves a durable change with no log entry — recovery can neither redo it consistently nor undo it, so the structure may stay inconsistent. (b) Forcing the log first means anything that reached the durable data is already described in the durable log, so the log is always at least as new as the data. (c) Because the log records every change that could be on disk, recovery can reconstruct or roll back to a consistent state from the log alone, without trusting the possibly-torn data. Tempting wrong answer: “the order doesn't matter as long as both are written” — the ordering is exactly what makes recovery correct. Feed-forward: §57.4.
57.7 (a) About 48× cheaper (916/19), since the log append is sequential and the data flush is random. (b) Group commit forces one fsync for a batch of many transactions' log records at once, amortizing the flush cost across commits while still forcing every record before its acknowledgment — so durability is unchanged. (c) Both convert scattered random writes into sequential ones: the LSM-tree for the data path, write-ahead logging for the durability path — same insight, different subsystem. Tempting wrong answer: “group commit weakens durability” — it only batches the flush; every record is still forced before its commit is acknowledged. Feed-forward: §57.4.
57.8 Step 4: The buffered log records are lost with the volatile state, so every write acknowledged since the last kernel flush is gone — breaking the durability promise that an acknowledged write survives a crash. The one-line fix: fsync (or open with synchronous flags) the log record and confirm it reached stable media before acknowledging the commit. If per-commit fsync is too slow, use group commit — batch many transactions' records into one forced flush — rather than dropping the force. Tempting wrong answer: “flush the data file more often to compensate” — the gap is the unforced log; flushing data does not restore the lost acknowledged writes. Feed-forward: §57.3–§57.4.
57.9 (a) Force policy — flush the whole data on commit. (b) Redo recovery — replay the log into a clean store. (c) Write-ahead rule — log record before data page. (d) Durability — acknowledged writes survive a crash. (e) No-force logging — force a small log record, write data lazily. Tempting wrong answer: confusing (a) force with (e) no-force — force flushes the data on commit; no-force defers it and relies on the log. Feed-forward: §57.2–§57.4.
57.10 (a) False — a write() only reaches the OS page cache; durability needs fsync to stable media. (b) False — the rule is the reverse: the log record must reach disk before the data page. (c) False — no-force means data pages are not forced on commit; they are still written back lazily. (d) True — sequential ~916 MB/s versus random ~19 MB/s. (e) True — redo replays logged changes in order to reconstruct the lost state. Tempting wrong answer: marking (c) true because “no-force” sounds like “never persist” — the data is persisted lazily, off the commit path. Feed-forward: §57.2–§57.4.
57.11 (a) Replaying all history costs time proportional to the whole log, which grows without bound; a checkpoint periodically records that everything up to some point is safely in the data on disk, so recovery can start near the end of the log instead of the beginning. (b) A real database lets changes from uncommitted transactions reach the log or data before an abort or crash; undo rolls those back — e.g., a transaction that updated a row and then crashed before commit must have that update undone so its effect does not persist. (c) A crash during replay must be recoverable, so redo must be idempotent — re-applying a logged change that was already applied must reach the same state — otherwise a second recovery pass could double-apply changes and corrupt the store. Tempting wrong answer: “committed-only redo is enough for a real database” — uncommitted changes that reached disk need undo too. Feed-forward: §57.5.
57.12 Open-ended and platform-specific. A correct write-up: (a) builds a store whose only durable artifact is an append-only log and appends plus fsyncs a record before each in-memory mutation; (b) applies a workload, discards the in-memory map to simulate a crash, replays the log, and asserts the recovered state equals the pre-crash state (this chapter: 163 keys lost and restored exactly from 1,000 records); (c) states toolchain and notes this is a deterministic, structural demonstration — the recovered state matches or it does not — not a wall-clock timing, and that moving the fsync after the mutation (or removing it) breaks the write-ahead rule and lets a crash lose acknowledged writes. Tempting wrong answer: “report the recovery time as the result” — the result is the correctness of recovery, not its speed. Feed-forward: §57.3.
