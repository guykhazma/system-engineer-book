Chapter 58 — Solutions

58.1 A transaction is a group of changes bracketed by begin and commit/abort that must take effect all-or-nothing (atomicity). A winner is a transaction that committed before the crash; a loser is one that was active at the crash and never committed. Tempting wrong answer: “a loser is a transaction whose changes were lost” — a loser is defined by not committing, not by what reached disk; its changes may well be on disk, which is exactly why undo is needed. Feed-forward: §58.1.
58.2 The after-image (the new value) is redo information — used to re-apply the change; the before-image (the old value) is undo information — used to reverse it. Tempting wrong answer: “only the new value, since recovery just replays” — that suffices only under no-steal; under steal you must also store the old value to roll uncommitted changes back. Feed-forward: §58.1.
58.3 Steal: the buffer pool may write a page dirtied by an uncommitted transaction back to disk (steal its frame). No-force: a transaction's data pages need not be forced to disk at commit — commit forces only the log. Tempting wrong answer: “no-force means data is never written” — data pages are written lazily; no-force only removes the force-at-commit requirement. Feed-forward: §58.2.
58.4 (a) A winner needs redo: under no-force its committed changes may not have reached disk, so recovery must re-apply them to keep durability. (b) A loser needs undo: under steal its uncommitted changes may have reached disk, so recovery must remove them to keep atomicity. (c) Redo only re-applies a change; when a loser's change is already on disk, re-applying it (or doing nothing) leaves it in place, whereas undo must erase it by restoring the before-image — the opposite operation. Tempting wrong answer: “recovery can just skip the loser's records” — skipping leaves the stolen change durable on disk; it must be actively rolled back. Feed-forward: §58.1–§58.2.
58.5 (a) No-steal + force: neither. No-steal + no-force: redo only. Steal + force: undo only. Steal + no-force: both. (b) No-steal + force needs neither, but it forces scattered data on every commit (random-write throughput, ~19 MB/s) and pins every dirty page until commit (crippling the buffer pool) — correct but slow. (c) Real engines pick steal + no-force: it buys free buffer eviction and log-only commit (fast), and the bill is implementing both redo and undo. Tempting wrong answer: “pick no-steal + force to avoid the complexity” — the performance cost is prohibitive; the complexity of redo+undo is the accepted price. Feed-forward: §58.2.
58.6 (a) T1's P2.c=5 was redone; it was missing because page P2 was never flushed, so under no-force the committed change lived only in the lost memory. (b) Redo repeats all history — winners and losers — so T2's lost P2.z=7 was also re-applied; undo sorts losers out afterward. (c) Undo restored T2's before-images (P1.a back to 1, deleting P2.z), leaving only T1's committed effects — the committed-only state. Tempting wrong answer: “redo skipped the loser's changes because they were uncommitted” — redo does not distinguish; it repeated them, and undo removed them. Feed-forward: §58.3.
58.7 (a) The page LSN stores the LSN of the most recent log record applied to that page, and is updated (and written to disk with the page) each time a change is applied to it. (b) Redo skips a record when its LSN ≤ the target page's page LSN (the change is already on the page); it re-applies only records whose LSN is greater. (c) After one redo pass every applied record's LSN is ≤ its page LSN, so every subsequent pass skips it — applying redo once or many times reaches the same state. Tempting wrong answer: “compare the LSN to the newest record in the log” — the comparison is against the page's LSN, which records how far that specific page has been brought up to date. Feed-forward: §58.4.
58.8 Step 4: Because T is a loser, atomicity requires that its change to r be erased — r must be restored to the value it held before T, namely 5. The redo-only log cannot do this: it recorded only r=8 (the after-image), and undo needs the before-image, 5, which was never logged — so there is no durable record of what to roll back to, and the stolen 8 is stuck on disk. The one-line fix: log the before-image as well as the after-image for every update (and, per the write-ahead rule, force it before the page is stolen). Tempting wrong answer: “re-run the transaction to overwrite r” — the transaction aborted; there is no correct value to re-derive without the before-image. Feed-forward: §58.1–§58.3.
58.9 (a) Redo — re-apply a committed change lost from disk. (b) Undo — roll back an aborted transaction's change. (c) Steal — evict an uncommitted dirty page. (d) No-force — commit forces only the log. (e) Page LSN — per-page high-water mark that lets redo skip. Tempting wrong answer: swapping (c) and (d) — steal is about eviction of uncommitted pages; no-force is about not forcing at commit. Feed-forward: §58.2–§58.4.
58.10 (a) True — under no-steal no uncommitted change ever reaches disk, so there is nothing to undo. (b) False — no-force means the pages may not be on disk at commit; only the log is forced, so redo is needed. (c) True — that is exactly the redo/undo split. (d) False — the page LSN is stored on the page (and written to disk with it); the log stores the record LSNs. (e) True — a crash can strike during recovery, so re-applying already-applied changes must be a no-op. Tempting wrong answer: marking (b) true because “committed sounds durable” — durability under no-force comes from the forced log, not from the data pages being on disk. Feed-forward: §58.2–§58.4.
58.11 (a) Scanning the whole log costs time proportional to all history, which grows without bound; a checkpoint periodically records the active transactions and the dirty pages (with the oldest not-yet-flushed LSN per page) so recovery can start its scan near the end of the log. (b) If a crash struck mid-undo and a re-run started undo from scratch, it could try to reverse changes it already reversed — double-undo — or roll back past a value later work depends on, corrupting the store; undo therefore needs a durable record of what it has already reversed so it can resume. (c) Redoing losers' changes first makes every page's page LSN reflect the true latest logged change on it, so the page LSN is a correct high-water mark for the whole log — undo can then proceed knowing history has been faithfully repeated, and undo's own actions are logged and redone the same way. Tempting wrong answer: “redoing losers is wasted work” — it is what keeps the page LSN and the redo/undo protocol uniform and restartable (Chapter 60). Feed-forward: §58.5.
58.12 Open-ended and platform-specific. A correct write-up: (a) builds a page store logging a before-image and after-image per change with a monotonic LSN and a per-page page LSN; (b) runs a committing and a non-committing transaction, flushes one page carrying the uncommitted change and loses one committed change, then redoes (skipping records at or below the page LSN) and undoes (restoring the loser's before-images); (c) asserts the recovered state equals the committed-only state (this chapter: recovered P1.a=1, P2.c=5), reruns redo to confirm zero records are applied, and explains that the zero-apply second pass is the evidence of idempotence — every change is now covered by its page LSN, so replay is a no-op and recovery is safe to restart. Tempting wrong answer: “report the recovery time” — the result is the correctness and idempotence of recovery, not its speed. Feed-forward: §58.3–§58.4.
