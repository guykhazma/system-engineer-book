Chapter 59 — Solutions

59.1 Because recovery scans the log from the first record, its cost is proportional to the log's total length, which grows the longer the database runs — so a long-lived, reliable system takes longer to recover. Tempting wrong answer: “because more data means more to reload” — it is the log length (number of records scanned), not the data size, that drives the cost; almost all of those records describe already-durable changes. Feed-forward: §59.1.
59.2 The active-transaction table (transactions in flight, each with its most recent LSN) — used by analysis to identify losers and by undo to know where to start rolling each back; and the dirty-page table (dirty pages, each with its recLSN) — used to compute the RedoLSN, where redo begins. Tempting wrong answer: “a list of committed transactions” — the checkpoint records the active ones; committed ones are settled and need no tracking. Feed-forward: §59.3.
59.3 A page's recLSN is the LSN of the oldest log record whose change might not yet be on that page — set when the page first goes from clean to dirty, and cleared when the page is flushed. Tempting wrong answer: “the LSN of the page's most recent change” — that is the page LSN; the recLSN is the oldest un-flushed change, and confusing the two silently loses data. Feed-forward: §59.3–§59.4.
59.4 (a) A sharp checkpoint quiesces the system (waits for all in-flight transactions to finish, refusing new work) and flushes every dirty page to disk before writing the checkpoint record. (b) The two costs: the quiesce is an unbounded stall (one long transaction holds the system hostage), and the full flush is a burst of scattered random writes (~19 MB/s) — exactly what no-force exists to avoid. (c) A fuzzy checkpoint records only the active-transaction and dirty-page tables; it can be taken without pausing or flushing because it merely snapshots the current state of play rather than forcing the disk up to date. Tempting wrong answer: “a fuzzy checkpoint is just a less frequent sharp one” — the difference is what it does (record tables vs quiesce-and-flush), not how often. Feed-forward: §59.2–§59.3.
59.5 (a) The workload is skewed — a small hot set takes most writes — and the background flusher steadily writes back the rest, so only the ~16 hot pages remain dirty; clean pages have left the dirty-page table. (b) The RedoLSN (1,964) sits near the log's end (2,041), so redo scans only the 77 records at or after it instead of all 2,040 — about 96.2% skipped. (c) The RedoLSN would stay near the end (the flusher keeps the dirty set and thus the minimum recLSN recent), so recovery would still scan roughly 77 records — recovery time stays bounded regardless of total log length. Tempting wrong answer: “a billion-record log means a billion-record recovery” — that is exactly what the checkpoint prevents; recovery tracks the un-flushed tail, not the history. Feed-forward: §59.3.
59.6 (a) Invariant: every change with an LSN below a page's recLSN is already on that page. (b) The RedoLSN is the minimum recLSN across dirty pages, so below it no page can have an un-flushed change — either the change's page is not dirty (already flushed) or it predates that page's recLSN (on the page by the invariant). (c) Hence any change with LSN below the RedoLSN is guaranteed durable, and redo may skip it without loss. Tempting wrong answer: “start redo at the checkpoint LSN” — the checkpoint LSN can be later than the RedoLSN; starting there would skip un-flushed changes made before the checkpoint but after their page went dirty. Feed-forward: §59.4.
59.7 (a) More frequent checkpoints cost extra work and log space, and — to keep the RedoLSN near the end — push the flusher to write dirty pages back sooner, giving up some no-force batching. (b) Rare checkpoints let the dirty set grow and the RedoLSN drift back, lengthening recovery. (c) Recovery time depends on the distance from the RedoLSN to the log's end (the un-flushed, unresolved work); a background flusher holds the dirty set — and thus the RedoLSN — within a target, bounding it. Tempting wrong answer: “checkpoint as often as possible” — past a point the steady-state overhead and lost batching outweigh the recovery savings; it is a tuned trade-off. Feed-forward: §59.4.
59.8 Step 4: With the RedoLSN at 150, redo begins after change A (LSN 100), so if A never reached P's on-disk copy it is never re-applied — the committed change A is silently lost. Recovery reports success because nothing detects the gap: the log replayed cleanly from the (wrong) RedoLSN and no invariant was checked. This is the most dangerous class of bug because it is a silent data loss — the database comes back “healthy” and short of committed writes, so it is discovered late, if ever. The one-line fix: set recLSN to the oldest un-flushed change (100), i.e., the LSN at which the page first went dirty, not its current page LSN. Tempting wrong answer: “redo will catch A because it scans the whole log” — redo starts at the RedoLSN precisely to avoid scanning the whole log; the wrong recLSN moves that start past A. Feed-forward: §59.4.
59.9 (a) RedoLSN — where redo begins. (b) Sharp checkpoint — quiesce and flush everything first. (c) recLSN — per-page oldest-un-flushed LSN. (d) Fuzzy checkpoint — record the tables without pausing. (e) Dirty-page table — the pages that might need redoing. Tempting wrong answer: confusing (c) recLSN with the page LSN — recLSN is the oldest un-flushed change, the page LSN the newest applied. Feed-forward: §59.2–§59.4.
59.10 (a) False — a fuzzy checkpoint flushes nothing; it only records the tables (that is why dirty pages remain and it is “fuzzy”). (b) False — dirty pages persist, so the on-disk data is not fully up to date after a fuzzy checkpoint. (c) True — the RedoLSN is the minimum recLSN. (d) False — recovery time depends on the distance from the RedoLSN to the log's end, not the total log length. (e) True — too-early recLSN redoes durable changes: slower, still correct. Tempting wrong answer: marking (b) true because a checkpoint “sounds like” a consistent snapshot — a sharp checkpoint leaves the disk clean, but a fuzzy one deliberately does not. Feed-forward: §59.2–§59.4.
59.11 (a) The database keeps running after the checkpoint is written — pages are dirtied and flushed — so the recorded table is stale by the crash; analysis replays the log forward from the checkpoint, adding pages to the dirty-page table when it sees their first change and (in full ARIES) accounting for flushes, so it rebuilds the table as of the crash. (b) Records before the checkpoint may still describe changes on pages that are still dirty (recLSN before the checkpoint), so they are needed for redo; only records behind the RedoLSN are provably durable and safe to recycle. (c) Undo starts from a loser's most recent LSN and walks its changes backward (via the per-record back-pointer); the checkpoint's recorded last-LSN per active transaction is where that walk begins. Tempting wrong answer: “the checkpoint's table is authoritative, so analysis can trust it as-is” — it is a stale starting point that the forward replay must update. Feed-forward: §59.5.
59.12 Open-ended and platform-specific. A correct write-up: (a) models a running store with a background flusher and a correct per-page recLSN (oldest un-flushed change); (b) takes a fuzzy checkpoint snapshotting the dirty-page table, computes the RedoLSN as the minimum recLSN, and counts records at or after it versus in the whole log; (c) reports the skipped fraction (this chapter: ~96%), asserts that no change below the RedoLSN is still dirty, and explains that this structural assertion — not elapsed time — is the evidence that the checkpoint both bounds recovery (few records scanned) and loses nothing (no un-flushed change skipped). Tempting wrong answer: “time the recovery to prove the checkpoint helps” — the guarantee is the record-count reduction and the safety assertion, both structural. Feed-forward: §59.3–§59.4.
