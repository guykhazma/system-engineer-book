Chapter 60 — Solutions

60.1 Analysis — scan from the checkpoint to find the losers and the RedoLSN. Redo — scan from the RedoLSN, repeating history by re-applying every change past its page LSN. Undo — scan backward, rolling back the losers and logging a compensation record per reversal. Tempting wrong answer: “redo, undo, analysis” — analysis must come first; redo and undo depend on the losers and RedoLSN it produces. Feed-forward: §60.1.
60.2 The loser set (transactions active at the crash with no commit), used by undo; and the RedoLSN (the minimum recLSN in the dirty-page table), used by redo as its starting point. Tempting wrong answer: “analysis redoes the changes” — analysis only reads the log and builds tables in memory; it touches no data page. Feed-forward: §60.2.
60.3 Repeat history means redo re-applies every logged change past its page LSN — committed or not — so the pages are reconstructed to the exact state they held at the instant of the crash, before undo removes the losers. Tempting wrong answer: “replay only the winners” — that is precisely what repeat-history does not do; redoing losers too is what keeps the passes simple and restartable. Feed-forward: §60.1.
60.4 (a) Analysis scans forward from the last checkpoint to the end of the log, reading update/commit/end records and updating the transaction table and dirty-page table in memory. (b) Redo starts at the RedoLSN; for each record it applies the change only if the record's LSN exceeds the target page's page LSN (otherwise the change is already on the page and it skips). (c) Undo processes a loser's changes newest-to-oldest (following the back-pointer chain), restoring each before-image and logging a CLR. Tempting wrong answer: “redo starts at the checkpoint” — it starts at the RedoLSN, which can be earlier than the checkpoint. Feed-forward: §60.2–§60.4.
60.5 (a) So the pages are reconstructed to the exact crash-time state, giving undo a consistent basis and every page a correct page LSN. (b) Immediately after redo the pages hold everything that existed at the crash — including losers' uncommitted values (in the run, P1={a:777}, P2={c:20,d:40}, P3={e:30}). (c) Two breakages: redo would need to know each transaction's fate before repeating its change (it does not, until analysis is fully digested per change), and the pages would reach a state that never actually existed, corrupting the page-LSN high-water marks that make redo idempotent. Tempting wrong answer: “redoing losers wastes effort and risks leaving their changes in” — undo removes them right after; the reconstruction is what makes undo and restart correct. Feed-forward: §60.1, §60.3.
60.6 (a) Redo re-applied T1's P2.c=20 (committed) and T3's P2.d=40 (loser), both missing because page P2 was never flushed. (b) The stolen pages already held T2's P1.a=777 and T3's P3.e=30, whose page LSNs already covered those records, so redo skipped them. (c) Undo restored P1.a to its before-image 10 (erasing 777) and deleted P2.d and P3.e, leaving P1.a=10, P2.c=20. Tempting wrong answer: “redo re-applied P1.a=777” — it skipped it; P1 was stolen with that value already on it. Feed-forward: §60.3–§60.4.
60.7 (a) The value it wrote (the before-image), so redo can replay the reversal after a crash; and the undoNextLSN, pointing to the next change still to be undone for that transaction, so undo can resume. (b) A CLR is redo-only because it records a reversal that has already been decided and must simply be re-applied on restart — undoing it would re-introduce the loser's change. (c) The one-way property guarantees recovery terminates: undo never generates new work to undo, so the rollback cannot loop. Tempting wrong answer: “a CLR is undone if we roll back further” — CLRs are never undone; the undoNextLSN chain skips past already-compensated changes. Feed-forward: §60.4.
60.8 Step 4: Undo resumes at LSN 41 (the last CLR's undoNextLSN), reverses the change at 41, then 40 — it does not re-reverse 42, because the persisted CLR advanced undoNextLSN past it. When T is fully undone it has three CLRs, one per original change (42, 41, 40), each written exactly once across the two runs. No change is undone twice because the durable CLR's undoNextLSN records that 42 was already compensated, so restart resumes below it rather than restarting the chain. Tempting wrong answer: “undo restarts at 42 and writes a fourth CLR” — the undoNextLSN exists precisely to prevent that re-reversal. Feed-forward: §60.4.
60.9 (a) Redo — re-apply every change past its page LSN. (b) Undo — reverse a loser's changes newest-to-oldest. (c) Compensation log record — logged as each reversal happens. (d) Analysis — rebuild the tables from the checkpoint. (e) Repeat history — reconstruct the exact crash-time state first. Tempting wrong answer: calling (a) “repeat history” — repeat history is the principle; (a) names the pass, redo, that implements it. Feed-forward: §60.1–§60.4.
60.10 (a) False — redo re-applies all changes past their page LSN, committed or not (repeat history). (b) False — undo runs last, after analysis and redo. (c) False — a CLR is redo-only and never undone; that is what guarantees termination. (d) False — analysis only reads the log and builds tables in memory; it does not touch data pages. (e) True — the undoNextLSN is exactly what lets undo resume rather than restart. Tempting wrong answer: marking (a) true because “only committed work should survive” — it should, but that is undo's job; redo faithfully repeats everything first. Feed-forward: §60.1–§60.4.
60.11 (a) A crash loses volatile memory but the disk survives; if the disk is lost or corrupted, the on-disk pages and page LSNs are gone, so recovery needs a prior backup plus an archived log spanning from the backup forward, replaying the archived log onto the restored backup (media recovery) rather than onto the live disk. (b) Physical byte-image logging is simple and idempotent but bulky and brittle to layout; logical operation logging is compact but hard to make idempotent and restartable (an operation's effect depends on current state); ARIES uses the physiological middle — physical to a page, logical within it — getting compact records that are still idempotent per page via the page LSN. (c) Recovery makes each transaction all-or-nothing across a crash, but says nothing about what concurrent transactions may observe of each other mid-flight; e.g., two transactions could produce a dirty read or a lost update — an isolation failure recovery does not address. Tempting wrong answer: “media recovery is just running ARIES again” — ARIES assumes the disk survived; a lost disk needs a backup and the archived log, not the live one. Feed-forward: §60.5.
60.12 Open-ended and platform-specific. A correct write-up: (a) builds a page store with a WAL carrying before/after-images and page LSNs and steals some pages to disk; (b) recovers in three passes — analysis (losers + RedoLSN), redo (repeat history, skipping records at or below the page LSN), undo (roll back losers, logging a CLR with an undoNextLSN per reversal); (c) crashes mid-undo, re-runs recovery, and asserts the final state equals both the committed-only state and a clean recovery (this chapter: P1.a=10, P2.c=20), explaining that each change being undone exactly once across the two runs — never re-reversed — is the evidence the CLRs made recovery restartable. Tempting wrong answer: “measure recovery time to show it works” — the guarantee is the state equality and the once-only undo, both structural. Feed-forward: §60.4.
