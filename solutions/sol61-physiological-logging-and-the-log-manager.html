Chapter 61 — Solutions

61.1 Physical — record the changed bytes (before- and after-images). Logical — record the operation and its arguments (“increment c by 5”). Physiological — record an operation on one named page (“insert into slot 3 of page P”), gated by that page's LSN. Tempting wrong answer: “physiological means logging both the bytes and the operation” — it means physical to a page, logical within it: one page, an operation, not a byte dump. Feed-forward: §61.1.
61.2 ARIES assumes physiological logging. “Physical to a page” means each record touches exactly one page, so that page's page LSN can gate its replay; “logical within it” means the change is described as an operation on the page's structure, not as raw bytes, which keeps the record small. Tempting wrong answer: “ARIES logs physically for safety” — pure physical is safe but bulky and brittle; physiological gets the same per-page idempotence far more compactly. Feed-forward: §61.1–§61.3.
61.3 All of a transaction's log records up to and including its commit record must be forced to durable storage (an fsync) before the commit is acknowledged to the client. Tempting wrong answer: “the data pages must be forced” — no; that is the whole point of no-force (Chapter 57). Only the log is forced at commit; the pages follow lazily. Feed-forward: §61.4.
61.4 (a) A physical redo record carries the after-image, so writing it once or many times leaves identical bytes — self-inverse against itself. (b) A logical record carries an operation whose effect depends on current state (“add 5”), so a second application changes the result again. (c) Physiological logging binds the operation to one page and gates it with the page LSN, so replay compares LSNs and skips a change already present. Tempting wrong answer: “logical redo is idempotent if the operation is deterministic” — determinism is not idempotence; “add 5” is deterministic yet double-counts. Feed-forward: §61.2–§61.3.
61.5 (a) The logical record “add 5 to b” carries no notion of “already applied,” so the forced second apply adds another 5, reaching {b:10}. (b) The physiological record's second apply compares its LSN (20) to the page LSN (now 20); since 20 is not greater than 20, it skips, leaving {b:5}. (c) The sizes (~64 B physical vs ~19 B physiological) illustrate that logging an operation on a page is far smaller than logging the page image, while still being replay-safe. Tempting wrong answer: “the physiological record stays 5 because the operation is a no-op the second time” — the operation is not a no-op; the page-LSN gate skips it. Feed-forward: §61.2–§61.3.
61.6 (a) Redo must be idempotent and restartable, and confining a record to one page lets that page's LSN gate replays — the only mechanism that makes redo safe to repeat. (b) Undo is made restartable by compensation records and their undoNextLSN chain (Chapter 60), not by a per-page mark, so it can span pages and act on the live structure. (c) A B-tree insert's key may have moved to another page after a later split, so undoing it (“delete key 5”) must re-locate the key in the tree as it is now — a logical operation, not a physical rewrite of the original page. Tempting wrong answer: “undo is logical because it is simpler” — it is logical because the structure may have changed; a physical undo would target bytes that have since moved. Feed-forward: §61.3.
61.7 (a) An fsync flushes everything in the log up to a point, so all commit records accumulated before it become durable together — many commits ride one sync. (b) Each transaction still blocks until the sync that covers its commit record completes, so no commit is acknowledged before it is genuinely on disk. (c) Group commit trades a little latency (waiting for a group to fill) for throughput (the expensive sync amortized over the group). Tempting wrong answer: “group commit lets a commit return before its sync” — no; it shares the sync, it does not skip it. Feed-forward: §61.4.
61.8 Step 3: The third record (LSN 35, replayed) is compared against the page LSN, which is now 35; since 35 is not greater than 35, redo skips it. The page LSN stays 35 and the page contents are unchanged, because the change at LSN 35 was already applied by Step 2. This demonstrates idempotence via the page LSN: a redo record has no effect once its LSN is at or below the page's. Tempting wrong answer: “the third record applies again and sets b=2 a second time, advancing the LSN to 36” — replay does not invent a new LSN, and the gate skips the already-applied record. Feed-forward: §61.3.
61.9 (a) Physiological logging — an operation on one page, LSN-gated. (b) Group commit — many commits, one fsync. (c) Physical logging — whole before/after page image. (d) Logical logging — just the operation. (e) Force-log-at-commit — records durable before acknowledgment. Tempting wrong answer: calling (a) “logical” — it is logical within a page, i.e. physiological; a bare logical record would not name the page or ride the page LSN. Feed-forward: §61.1–§61.4.
61.10 (a) False — logical redo is not idempotent; replaying “add 5” double-counts. (b) True — physiological logging binds each redo record to a single page. (c) False — group commit shares the sync but never acknowledges a commit before its record is durable. (d) True — carrying the after-image is exactly what makes physical redo self-inverse against itself. (e) False — ARIES undo is logical; only redo is page-oriented. Tempting wrong answer: marking (a) true because the operation is deterministic — deterministic is not idempotent. Feed-forward: §61.2–§61.4.
61.11 (a) Choose the group-fill timeout by watching commit latency versus throughput: too long and single committers stall waiting for a group that never fills (latency spikes at low load); too short and the sync is barely amortized (throughput stays near one-per-sync at high load). A good policy adapts — flush when the group reaches a size or a small timer expires, whichever comes first. (b) Log a two-page split as two physiological redo records, one per page, each LSN-gated, plus enough information (or a nested top-action) that recovery either applies both or neither; each page's redo stays idempotent because each record is confined to its own page and gated by its own page LSN. (c) The fsync count is fixed by the arithmetic (N commits, groups of G, gives ceil(N/G) syncs) and is identical on any machine; the times depend on the device's sync latency and the rest of the commit path, so they are a measurement, not a constant. Tempting wrong answer: “pick the largest timeout for maximum batching” — that maximizes throughput but can ruin latency at low load, where groups fill slowly. Feed-forward: §61.4.
61.12 Open-ended and platform-specific. A correct write-up: (a) builds three records for one change and applies each twice, asserting physical and physiological are unchanged (the page LSN gates the physiological replay) while the logical one double-counts; (b) writes N commit records with one fsync per commit and one per group of G, reporting fsync count and elapsed time; (c) identifies the fsync count as the structural constant (ceil(N/G), machine-independent) and the times as measurements, and notes durability is identical because both modes force every commit's record before acknowledging it. Tempting wrong answer: “report only the elapsed times as the result” — the portable, reproducible claim is the sync count and the idempotence outcomes; the times illustrate the effect on one machine. Feed-forward: §61.4.
