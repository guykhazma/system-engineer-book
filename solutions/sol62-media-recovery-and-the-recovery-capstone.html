Chapter 62 — Solutions

62.1 Transaction failure (an abort) — handled by undo. System failure (a crash) — handled by ARIES's redo and undo over the surviving disk. Media failure (the disk lost or corrupted) — handled by restoring a backup and rolling the archived log forward. Tempting wrong answer: “a crash and a media failure are the same failure” — a crash preserves the disk; a media failure destroys it, which is why one needs ARIES and the other needs copies kept elsewhere. Feed-forward: §62.1.
62.2 A backup — a copy of the data pages as of a past LSN, giving a known-good base — and an archived log — a copy of the log records on separate storage, spanning from the backup forward, giving every change since. Tempting wrong answer: “just the backup; the log is only for crashes” — a backup alone loses everything after it; the archive is what rolls forward to the present. Feed-forward: §62.2.
62.3 A full roll-forward replays the archived log to the end, reaching the pre-failure state; point-in-time recovery stops the roll-forward at a chosen moment, reaching an earlier state and excluding later records. Tempting wrong answer: “PITR undoes records after the point” — it never replays them in the first place; there is nothing to undo. Feed-forward: §62.3.
62.4 (a) ARIES reads the data pages and the log, both from stable storage. (b) A media failure destroys that storage, so the pages and log are gone — the run shows an empty store {}, with no page to compare a page LSN against and no record to redo. (c) The write-ahead log gives crash recovery because a crash preserves the disk the log lives on; it gives no media protection because the disk's loss takes the log with it. Tempting wrong answer: “ARIES could rebuild the pages from the log” — the log died with the disk; there is nothing to rebuild from. Feed-forward: §62.1.
62.5 (a) Restoring the backup alone reaches the backup instant — {P1:100, P2:200} as of LSN 2 — losing every change after it (LSNs 3–6). (b) Replaying the archived log onto it re-applies those changes, rolling the state forward from the backup toward the present. (c) The backup bounds how much log must be replayed and the archive bounds how much data is lost, so together they reach any moment the archive spans. Tempting wrong answer: “the backup already has the recent changes” — it is frozen at its LSN; only the archive carries what came after. Feed-forward: §62.2.
62.6 (a) Because the six records describe exactly the changes that followed the backup, so replaying them onto the backup reproduces the live disk at the crash — {P1:999, P2:1}. (b) The records are idempotent physiological redo records (Chapter 61), so replaying them onto the restored pages is safe and deterministic. (c) A backup at LSN 4 would need only records 5–6 replayed to reach the same end state — a shorter roll-forward, hence faster restore. Tempting wrong answer: “replaying the log could double-apply a change” — idempotence prevents that; each record applies to the state it describes. Feed-forward: §62.3.
62.7 (a) Stopping at LSN 4 replays only records 1–4 (through the legitimate transfer), reaching {P1:150, P2:150}; the bad writes at LSN 5–6 are never replayed. (b) PITR addresses a valid-but-wrong change the disk recorded correctly (a bad migration, an errant bulk update); crash recovery and full roll-forward would loyally reproduce it, because the disk did exactly what it was told. (c) The recovery-point objective is set by how far the archive lags; the recovery-time objective by how much log must be replayed since the last backup. Tempting wrong answer: “ARIES would undo the bad migration since it wasn't a real transaction” — it was a committed transaction; only PITR's early stop excludes it. Feed-forward: §62.3.
62.8 Step 3: Roll-forward must stop at LSN 16 — replaying records 11 through 16 and not 17 through 20. This reaches the state just before the mistaken delete because record 17 (the delete) is never applied, while a full roll-forward to LSN 20 would replay 17 and faithfully reproduce the delete, since the disk recorded it as a legitimate committed change. No later record is undone; they are simply not replayed. Tempting wrong answer: “stop at 17 so the delete is included but nothing after” — stopping at 17 replays 17 and reproduces the mistake; you must stop before it, at 16. Feed-forward: §62.3.
62.9 (a) Media failure — a dead drive taking pages and log. (b) Backup — a copy of the pages as of a past LSN. (c) Point-in-time recovery — stopping roll-forward before a bad migration. (d) Transaction failure — an abort reversed by undo. (e) Archived log — log records on independent storage. Tempting wrong answer: calling (a) a “system failure” — a system failure (crash) spares the disk; a dead drive is a media failure. Feed-forward: §62.1–§62.3.
62.10 (a) False — ARIES needs the surviving disk; a destroyed disk needs a backup and archived log. (b) True — a backup alone loses everything after it. (c) True — PITR stops roll-forward before a correctly-recorded write, which crash recovery would reproduce. (d) False — an archive on the same volume dies with it; it must be on independent storage. (e) True — roll-forward replays the archived log onto the restored backup. Tempting wrong answer: marking (a) true because “recovery is provably correct” — correct only when the disk survives. Feed-forward: §62.1–§62.3.
62.11 (a) Incremental backups copy only the pages changed since the last backup, so each backup is cheap and frequent, but restore must apply the last full backup plus every incremental since, trading a slower, multi-step restore for lower backup cost and I/O. (b) If a stretch of archived log is missing, roll-forward cannot cross the gap — every change after it is unreachable, so recovery halts at the gap's start; detect it by checking that archived-log LSNs are contiguous (no missing range) as part of the periodic test-restore, before a real disaster needs them. (c) A single node's mechanisms do not cover the loss of the whole node or site (fire, region outage) while it must stay available, nor divergence between replicas — that is replication and distributed systems (Volume 3), beyond durability. Tempting wrong answer: “incremental backups have no downside” — they trade a slower, more fragile restore for cheaper backups. Feed-forward: §62.4.
62.12 Open-ended and platform-specific. A correct write-up: (a) builds a page store with a redo log, runs a workload, takes a full backup partway, and archives the log separately; (b) discards the on-disk pages, restores the backup, rolls the archived log forward, and asserts the result equals the pre-failure state (this chapter: {P1:999, P2:1}); (c) repeats with roll-forward stopped before a bad write and asserts the earlier state ({P1:150, P2:150}), explaining that an archive on the same discarded disk would have been destroyed with it, leaving only the stale backup. Tempting wrong answer: “keep the archive with the database for convenience” — that is exactly the failure the lab exists to expose. Feed-forward: §62.2–§62.4.
