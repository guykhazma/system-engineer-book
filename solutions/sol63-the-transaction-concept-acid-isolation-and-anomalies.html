Chapter 63 — Solutions

63.1 Atomicity — all of a transaction's changes take effect or none do. Consistency — a transaction preserves the application's invariants. Isolation — concurrent transactions do not see each other's uncommitted state. Durability — committed changes survive any failure. Tempting wrong answer: “Consistency means the replicas agree” — that is a distributed-systems sense; in ACID it means invariants are preserved across the transaction. Feed-forward: §63.1.
63.2 Part X built Atomicity (undo) and Durability (the WAL and ARIES); Part XI is about Isolation. Tempting wrong answer: “Part X built consistency” — consistency is the application's contract, upheld using the other properties; the two Part X mechanized are atomicity and durability. Feed-forward: §63.1.
63.3 Serializability means an interleaved schedule's effect equals that of some serial order of the same transactions — the correctness gold standard for concurrency. Tempting wrong answer: “serializable means the transactions ran one at a time” — they may interleave heavily; what matters is that the effect equals some serial order. Feed-forward: §63.1.
63.4 (a) T1 reads 100; T2 reads 100; T1 writes 110; T2 writes 120 (computed against the 100 it read, not T1's 110) — T1's +10 is overwritten and lost. (b) Every operation was legal, every value read was committed, no constraint was violated, and both transactions committed, so recovery reproduces exactly this state — nothing “failed.” (c) Raise isolation to REPEATABLE READ or SERIALIZABLE (which forbid the lost update), or make the update atomic in the database (UPDATE ... SET bal = bal + n under one lock). Tempting wrong answer: “a UNIQUE or CHECK constraint would catch it” — no constraint is violated; the final value is a legal number, just the wrong one. Feed-forward: §63.2.
63.5 Dirty read: T2 reads T1's uncommitted 50, which T1 then rolls back — observed 50 vs committed 100. Lost update: two read-modify-writes, T2's write overwrites T1's — 120 vs serial 130. Non-repeatable read: T1 reads a row, T2 updates and commits, T1 re-reads — 100 then 200. Phantom: T1 runs a predicate query, T2 inserts a matching row and commits, T1 re-runs — SUM 120 then 150. Tempting wrong answer: “the non-repeatable read and phantom are the same” — one is a changed existing row, the other a newly inserted row matching a predicate. Feed-forward: §63.3.
63.6 (a) A non-repeatable read is an existing row changing value between two reads; a phantom is a new row appearing in a predicate's result set between two queries. (b) Locking the rows you read pins their values, preventing the non-repeatable read; but a phantom is a row that did not exist when you read, so there was no row to lock. (c) You must lock the predicate (or a range covering it), which is more expensive because it constrains rows that do not yet exist, blocking inserts that would match. Tempting wrong answer: “lock the table to stop phantoms” — a predicate/range lock is the targeted mechanism; a full table lock works but needlessly serializes unrelated inserts. Feed-forward: §63.3.
63.7 (a) READ UNCOMMITTED — none; READ COMMITTED — dirty read; REPEATABLE READ — dirty read, non-repeatable read, lost update; SERIALIZABLE — all four including the phantom. (b) READ COMMITTED only forbids reading uncommitted data; both writers in a lost update read committed values, so the level is satisfied while the update still vanishes. (c) SERIALIZABLE must prevent phantoms, which requires locking predicates or ranges (not just rows), constraining rows that do not yet exist and serializing more. Tempting wrong answer: “REPEATABLE READ forbids phantoms” — it forbids non-repeatable reads and lost updates but still permits phantoms; SERIALIZABLE adds the phantom. Feed-forward: §63.4.
63.8 Step 3: The second query returns S + 40 — larger than the first, because the newly inserted EU order matches the predicate. This is a phantom. SERIALIZABLE would prevent it (REPEATABLE READ would not, since it still permits phantoms). Row-locking the rows read by the first query does not prevent it because the inserted row did not exist at the first query, so there was no row to lock; only a predicate/range lock on region='EU' would block the insert. Tempting wrong answer: “REPEATABLE READ fixes it because the reads are repeated” — repeatable read stabilizes existing rows, not the appearance of new ones. Feed-forward: §63.3–§63.4.
63.9 (a) Dirty read — reading a value later rolled back. (b) Serializability — effect equals some serial order. (c) Lost update — one write overwrites another. (d) Phantom — a predicate query returning a larger set after an insert. (e) READ COMMITTED — forbids dirty reads and nothing else. Tempting wrong answer: calling (d) a non-repeatable read — a non-repeatable read is a changed existing row, not a new row appearing. Feed-forward: §63.3–§63.4.
63.10 (a) True — with one transaction at a time, none can see another's in-progress state. (b) False — recovery preserves committed writes but does not order concurrent ones; the lost update commits cleanly. (c) False — READ COMMITTED permits non-repeatable reads; it only forbids dirty reads. (d) True — a phantom is a newly inserted (or deleted) row matching a predicate, not a change to an existing one. (e) True — that is the definition of serializable. Tempting wrong answer: marking (b) true because “the database is ACID” — the I must be enforced separately; A and D do not imply it. Feed-forward: §63.1–§63.4.
63.11 (a) The lost update satisfied atomicity (each transaction was all-or-nothing) and durability (both writes survive), yet the result is wrong — so correctness under concurrency is a property those two do not provide, proving isolation is separate. (b) Snapshot isolation gives each transaction a consistent snapshot and forbids the four named anomalies, but two transactions can each read the snapshot, update different rows based on what they read, and commit — a “write skew” whose combined effect matches no serial order; forbidding the enumerated anomalies is weaker than requiring serial-equivalence. (c) A lock on the balance held by T1 from its read until commit would block T2's read (or write), forcing T2 to act on T1's committed 110 and reach 130; the cost is that T2 waits, reducing concurrency on that row. Tempting wrong answer: “snapshot isolation is serializable because it blocks the four anomalies” — write skew shows it is not. Feed-forward: §63.2, §63.4.
63.12 Open-ended and platform-specific. A correct write-up: (a) encodes four interleaved schedules, one per anomaly, each reporting observed vs serial-equivalent; (b) asserts each observed value differs from the correct one (dirty read 50 vs 100, lost update 120 vs 130, non-repeatable 100 vs 200, phantom 120 vs 150); (c) adds a rule blocking T2's read until T1's write commits, showing the lost update reaches 130, and identifies the rule as approximating a level that forbids the lost update (REPEATABLE READ / SERIALIZABLE) at the cost of T2 waiting. Tempting wrong answer: “measure throughput to show the anomaly” — the anomaly is a structural mismatch between observed and serial-equivalent values, not a timing. Feed-forward: §63.2–§63.4.
